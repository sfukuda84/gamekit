# gamekit-bootstrap スキル（ゲームの立ち上げ: G0 → G14）

1 文のアイデアから、機能ごとの仕様化と実装（`gamekit-all`）に入れる状態（面白さの仮説と検証、デザインの柱、システムと目標値、エンジン、憲章、機能の一覧、共通基盤、非機能要件、デザインの決め事）までを、1 つの流れで作る。各ステップの中身は、それぞれのスキルの SKILL.md に従う。**このファイルには、順番と引き継ぎだけを書く。**

パスは `.gamekit/config.yaml` の `paths` で読み替える。以降、`$GK` は `python3 <skills>/gamekit-status/scripts/gamekit.py` を表す（`<skills>` は、このスキルが置かれた skills ディレクトリ）。

## 1. 引数

```text
$ARGUMENTS
```

`--auto` と `--oneshot` は実行モードの指定であり、位置を問わない。取り除いた残りを、1 文のアイデア（G1 の入力）か、各ステップへの追加の希望として扱う。

| 指定 | モード | 動作 |
|---|---|---|
| なし | 対話 | 各ステップのスキルの手順どおりに、ユーザーに質問し、合意を得ながら進める |
| `--auto` | 自動 | ユーザーに一度も質問せず、推奨案を採用して最後まで進める（§7） |
| `--oneshot` | 一括質問 | G0 で一度だけ、影響の大きい論点をまとめて質問する。以降は `--auto` と同じく自動で進める（§7） |

両方が指定されたときは `--oneshot` として扱う。

`--adopt` は、既存のゲームプロジェクトに取り込んだ後（`new_project.py --adopt`）に使う指定であり、位置を問わない。上のどのモードとも組み合わせられる。付けると、G0 の後に §8 の取り込みの計画を作り、ステップごとに「移し替える / 完了として記録 / 新しく作る / 飛ばす」を決めてから進める。

各ステップのスキルには、自動モード・一括質問モードのとき `--auto` を付けて呼んだものとして扱う。

## 3. 進捗の記録と再開

- 各ステップが終わったら、次のようにコミットする。変更がなくても空コミットで記録する。

  ```bash
  git add -A
  git commit --allow-empty -m "<§2 の subject>" -m "Gamekit-Bootstrap: <ステップ>"
  ```

- ステップのスキルを単独で実行したとき（例: `/gamekit-seed`）も、同じ形で記録する。各スキルの「出力」の節にある「G<n> を記録する」は、この形のコミットを指す。
- Claude Code のクラウドセッション（環境変数 `CLAUDE_CODE_REMOTE` が `true`）では、コミットのたびに `git push -u origin HEAD` で作業ブランチを push する。push に失敗しても止まらず、失敗したことを完了報告に挙げる。ローカルでは push しない。
- 開始時に `$GK bootstrap` で完了済みのステップ（`COMPLETED_STEPS`）と次のステップ（`NEXT_STEP`）を調べ、`NEXT_STEP` から再開する。`DONE` なら立ち上げは完了しているので、完了報告の「次の案内」だけを示す。
- 記録がなくても成果物がそろっているステップ（`--adopt` で取り込んだプロジェクトに多い）は、内容を確かめる。対話モードでは、完了として記録してよいかをユーザーに確かめる。自動モード・一括質問モードでは確かめずに記録し、再開するステップを示すだけにする。
- 成果物が既存の別の資料にある場合（例: `docs/design/systems.md`、`docs/specs/game-design.md`）は、そのステップのスキルの取り込み（更新モード）で gamekit の様式に移し替えてから記録する。元の資料は動かさない・消さない。
- 再開する場合は、完了済みのステップと再開するステップをユーザーに示してから進める。

## 4. 手順

### G0: 事前確認と初期化

1. Git リポジトリのルートで、ブランチが `main` であり、未コミットの変更がないことを確かめる。Claude Code のクラウドセッションでは、`main` の代わりにセッションの作業ブランチにいればよい。満たさない場合は、ユーザーに状況を示して対応を確かめる（自動モード・一括質問モードでは止まる。§7「止まる場面」）。Git リポジトリでなければ、`git init -b main` してよいかを確かめてから初期化する（自動モードでは初期化する）。
2. `.gamekit/config.yaml` がなければ `$GK init` で作る。既存のファイルは変えない。
3. `docs/concept/` に、`.gitkeep` 以外のアイデアのファイル（`core-concept.md`、`seed.md` など）があることを確かめる。ない場合は、引数のアイデアを `docs/concept/core-concept.md` に書く。引数にもなければ、次のように聞く（自動モードでは止まる。`--adopt` のときは聞かずに 5 へ進む）。

   > 作りたいゲームを 1 文で教えてください。「〇〇になって△△するゲーム」でも、遊びの断片でも、オマージュしたい作品名だけでも構いません。対象のプラットフォーム（PC／スマホ／ブラウザ／コンソール）が決まっていれば、それも添えてください。

4. 引数でアイデアへの追記があれば、`core-concept.md` の末尾に「追記（YYYY-MM-DD）」の節として足す。
5. `--adopt` のときは、§8 の取り込みの計画を作って合意を得る（3 のアイデアがなくても止まらない。既存の企画書や `docs/concept/` の資料をアイデアとして扱う）。
6. `--oneshot` のときは、§7 の一括質問を行う。`--adopt` と組み合わせたときは、既存の資料から決まる論点を除いて選ぶ。
7. 変更があれば、`chore(game): gamekit を初期化` でコミットする（trailer なし）。`new_project.py` で作ったプロジェクトで変更がなければ作らない。

### G1〜G13

各スキルの手順を最後まで行う。ヒアリング、調査、案の比較、合意、検証を省かない。各ステップの終わりに §3 の形で記録する。

引き継ぎの注意:

- **G1 → G2**: `seed.md` の「調査の論点」と「参考作品の候補」が G2 の入力になる。オマージュ元が挙がっていれば、G2 で必ず調べ、IP の注意点を書かせる。
- **G2 → G3**: 重なりが大きい参考作品を、G3 の「参考作品との差」で必ず扱う。
- **G3 → G4**: 選ばなかった案は `backlog.md` に残る。G4 の壁打ちで要素を拾い直してよい。
- **G4 → G2（戻り）**: 壁打ちでジャンルやコアファンタジーが大きく変わったら、G2 に戻って再調査する。対話モードでは戻るかを確かめる。自動モードでは戻らず、`docs/auto-decisions.md` に記録する。
- **G4 → G5**: GP4（コアループ）と GP5（主要な意思決定）の確定内容を、`core-loop.md` の出発点にする。GP12（IP・オマージュの境界）は `pillars.md` の「やらないこと」にも写す。
- **G5 → G6 → G5（戻り）**: G6 で仮説が棄却されたら、`gamekit-prototype` の手順で `core-loop.md`・`pillars.md` を直す。直した後に、もう一度 G6 の該当する仮説を検証する。同じ仮説の棄却が 2 回続いたら、対話モードではユーザーに方向性の見直し（G3・G4 に戻るか）を確かめる。自動モードでは止まる（§7）。
- **G6 → G7**: 机上シミュレーションで得た数値（1 ループの時間、資源の増え方など）を、`targets.md` の根拠にする。
- **G7 → G8**: 決定性（同じシードで同じ結果）やシミュレーションの要否は、エンジンとテストの方式の選び方に効く。`targets.md` を検算するシミュレーションの実行方法を、`docs/architecture.md` と `config.yaml` の `commands.balance_sim` で決めさせる。
- **G8 → G9**: §4 G9 の入力を渡す。
- **G9 → G10**: 機能は「プレイヤーが遊べる単位」で切り、最初の数件で垂直スライス（GP10）が遊べる順に並べる。共通基盤・リリース基盤の候補は機能にせず、`docs/feature/premises.md` に記録させる（G11・G12 で使う）。番号 `000` と `999` は使わない。
- **G10 → G11・G12**: 共通基盤の候補を G11 で `000-game-foundation.md` に、リリース基盤の候補を G12 で `999-game-release.md` にまとめる。
- **G12 → G13**: `docs/nfr.md` のアクセシビリティとローカライズの水準を、`EXPERIENCE.md` と `FEEL.md` に引き継ぐ。
- **仮題**: G1・G4 で仮題を決めたり変えたりしたら、`.gamekit/config.yaml` の `title` も更新する。

### G9: 憲章

`speckit-constitution` の手順で `.specify/memory/constitution.md` を作る。原則の案を作るときは、次を入力として渡し、ユーザーの確認を取る。

- ゲーム開発と言語のルール（`.kiro/steering/` の各ファイル）
- デザインの柱（`docs/game/pillars.md`）。例: 「すべての機能はデザインの柱に従う。柱に反する機能は、柱の見直し（gamekit-core の更新モード）を経てから作る」
- 数値はデータに置く。例: 「調整値はマスタデータ（`paths.data`）に置き、コードに直接書かない。機能ごとに `tuning.md` を作り、`gamekit-balance check` で目標値を確かめる」
- 決定性。例: 「乱数はシードを指定できる生成器だけを使い、同じシードと入力で同じ結果になる」（ゲームの性質上、要らないと判断したらその理由を書く）
- `docs/architecture.md` のエンジンと構成。例: 「エンジンと構成は docs/architecture.md に従う。変える場合は gamekit-architecture の見直しを経る」
- 非機能要件とデザインの参照。例: 「すべての機能は docs/nfr.md と docs/design/ に従い、plan.md の憲章チェックで確かめる」（`docs/nfr.md` は G12、`docs/design/` は G13 で作る）
- テストの方針（テストファーストにするか、ロジックとデータの検証をどこまで自動化するか、プレイ確認を `[人]` のタスクにすること）は、ユーザーに質問して決める。

## 6. 規則

- 各ステップの中身は、それぞれのスキルの SKILL.md に従う。このスキルで手順を省いたり、ヒアリングを飛ばしたりしない。自動モード・一括質問モードでは、ヒアリングや合意の手順を §7 の規則で置き換える（調査、比較、机上検証、書き出し、検証は省かない）。
- ユーザーが「このステップは後でやる」と明示した場合は、そのステップを飛ばして次に進んでよい。完了報告に、飛ばしたステップと影響を書く。飛ばしたステップは記録しない（再実行時に再開の対象になる）。ただし G5（柱とコアループ）と G9（憲章）は、後のステップがすべて前提にするので飛ばせない。飛ばしたいと言われたら、影響を示して確かめる。
- G6 の机上検証は、AI が実行できるもの（紙のプロトタイプの手順の机上プレイ、表計算や Python のシミュレーション）を実際に行う。グレーボックスでのプレイは人の作業なので、計画を書いて「保留（プレイで確かめる）」とし、立ち上げは止めない。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。

## 7. 自動モード（`--auto`）と一括質問モード（`--oneshot`）

どちらのモードも、各ステップのスキルでユーザーに聞く論点（ヒアリング、案の選択、書き出し前の合意など）を、エージェント自身が作る推奨案で決めて進める。違いは、最初に一度だけ質問するかどうかである。

立ち上げで決めることは、ジャンル、規模、プラットフォーム、収益化、オマージュの境界など、ユーザーしか知らない前提を多く含み、後のすべての機能の土台になる。そのため、自動で決めたことは**仮定**として扱い、そうと分かる形で記録して、後から見直せるようにする（下の「記録」）。各スキルの「推測で埋めない」は、このモードに限り「推奨案を仮定として明示して採用し、記録する」に置き換える。

### 一括質問（`--oneshot` の G0）

G0 の 1〜4 の後で、次の候補のうち、アイデア（`docs/concept/`）と引数から決まらないものを上から順に最大 4 つ選び、AskUserQuestion の 1 回にまとめて質問する。各問には推奨案を先頭に `(Recommended)` 付きで置く。

| 順 | 論点 | 使うステップ |
|---|---|---|
| 1 | ジャンルと主なプラットフォーム（PC／スマホ／ブラウザ／コンソール）、操作の方式（GP3） | G1、G3、G4、G8、G12 |
| 2 | 規模と期間（作る人数、最初に遊べる版までの期間、垂直スライスの範囲。GP10） | G3、G4、G10 |
| 3 | 使いたい、または得意なエンジンと言語（Godot GDScript／Godot C#／Web の TypeScript など） | G8 |
| 4 | 収益化の方式（買い切り／無料＋課金／広告／未定・趣味。GP11） | G4、G10、G12 |
| 5 | オマージュ元・参考にしたい作品と、持ち込まない境界（GP12） | G1、G2、G4 |
| 6 | 1 回に遊ぶ長さと、遊ぶ場面（GP2） | G4、G5、G7 |
| 7 | 目指す見た目と手触り（ドット絵／3D／手描き、気持ちよさの方向） | G13 |

- 回答は `docs/concept/core-concept.md` の末尾に「追記（YYYY-MM-DD、一括質問の回答）」の節として書き、`docs(bootstrap): 一括質問の回答をアイデアに追記` でコミットする（trailer は付けない）。アイデアに書くので、以降のスキルは回答を「確定」の根拠として使える。
- 再開したときに、この節がすでにあれば質問しない。
- 質問はこの 1 回だけにする。回答から新しい論点が出ても、以降は自動モードで決める。

### 各ステップでの自動の決め方

| ステップ | 論点 | 自動モードでの動作 |
|---|---|---|
| G0 | ブランチが `main`（クラウドセッションでは作業ブランチ）でない、未コミットの変更がある | 止まる（下の「止まる場面」） |
| G0 | アイデアがない | 引数に追記や希望以外のテキストがあれば、それをアイデアとして `core-concept.md` に書く。なければ止まる |
| G1 | ピッチ案の選択 | 採点が最も高い案を採る（`gamekit-seed` の自動モード） |
| G2 | 追加の調査観点 | 追加しない。Web を調べられない環境では「未調査」と書いて進め、見直しの優先度を「高」にする |
| G3 | 3 案からの選択 | 推奨案を採る。ジャンル、プラットフォーム、規模は見直しの優先度を「高」にする |
| G4 | GP1〜GP12 の未決の項目 | 種・方向性・調査から推奨案を作って採用し、状態を「確定」にする。質疑記録は `#### Q<n>（ラウンド 1, auto）— <項目 ID>` とし、回答の頭に `(auto: 仮定)` を付けて根拠を書く |
| G5 | 柱の案、コアループの合意 | 推奨案を採る。柱は見直しの優先度を「高」にする |
| G6 | 検証の方法、判定 | AI が実行できる方法を選んで実際に行い、結果で判定する。人のプレイが要る仮説は「保留」にする |
| G7 | 経済と成長曲線の式、目標値 | G6 の数値と参考作品の調査から推奨値を採る。根拠が推測だけの目標値は見直しの優先度を「高」にする |
| G8 | エンジンの 3 案からの選択、言語、データの形式 | 推奨案を採る。根拠がなければ、無料で導入でき、ヘッドレスで自動テストとシミュレーションを回しやすく、対象のプラットフォームに出せる案を採る。見直しの優先度は「高」 |
| G9 | 憲章の原則の確認、テストの方針 | 推奨案を採る。テストの方針は、ロジックとデータの検証をテストファースト、手触りは `[人]` のプレイ確認を既定にする。批准日など不明な日付は実行日にする |
| G10 | 分割案の合意、着手順 | 提示せずに書き出す。着手順は垂直スライスが最短で遊べる順にする。分割案は完了報告に載せる |
| G11 | 共通基盤の範囲、書き出しの合意 | 各機能の要求から必要と判断できるものを最初の公開の範囲に入れ、それ以外は「後で入れる」として backlog に足す |
| G12 | 目標値、999 の位置、書き出しの合意 | エンジンと対象端末で達成できる推奨値を採る。999 の位置は既定（最初の公開の範囲の最後）にする |
| G13 | アートの方向、画面の構成、手触りの水準 | `gamekit-design` の自動モードで決める。アートの方向と主な端末は見直しの優先度を「高」にする |
| G14 | 整合の食い違い | 該当するスキルの更新モードの手順で、推奨の修正を当てる |

### 止まる場面

次の場面では自動で進めず、止まった理由とユーザーに判断してほしい事項（選択肢と推奨案）を報告して終了する。判断した後にもう一度 `gamekit-bootstrap` を実行すれば（モードの指定は問わない）、続きのステップから再開する。

- G0 で、ブランチが `main`（クラウドセッションでは作業ブランチ）でない、または未コミットの変更がある
- G0 で、アイデアがなく、引数にもない（`--adopt` で既存の資料をアイデアとして扱える場合を除く）
- `--adopt` の計画で、ユーザーが書いた資料を上書き・移動しないと進められない場合（§8）
- G6 で、同じ仮説の棄却が 2 回続いた（方向性の見直しはユーザーが決める）
- G14 の検証エラー、または G10 の `validate.py` のエラーが、3 回直しても 0 件にならない

### 記録

- 自動で決めたことは、すべて `docs/auto-decisions.md` に追記する。ステップごとに節を分け、1 件ごとに次を書く。
  - 論点、採用した案、ほかの選択肢、理由
  - 根拠の種類（アイデア / 一括質問の回答 / 調査 / 机上検証 / 推測）
  - 見直しの優先度（高 / 中 / 低）。ジャンル、プラットフォーム、規模、収益化、デザインの柱、エンジン、オマージュの境界、根拠が推測だけのものは「高」にする
  - 反映したファイルと、見直すときに使うスキル（例: `gamekit-sparring`、`gamekit-core` の更新モード、`gamekit-architecture` の更新モード）
- 各ステップのコミットに `docs/auto-decisions.md` の更新を含める。
- サブエージェントに調査などを任せたときは、記録すべき判断をサブエージェントの最終回答で返させ、記録は親が行う。

## 8. 取り込みモード（`--adopt`）

既存のゲームプロジェクト（speckit で進めていた、または手書きの資料で進めていた）に gamekit を入れたときに、すでにある資料を gamekit の成果物に移し替えて、機能の工程（`gamekit-all`）に入れる状態にする。**元の資料は動かさない・消さない・書き換えない。** 移し替えた成果物の冒頭には、出典の元ファイル（パスと、読んだ時点のコミット）を書く。

### 8.1 資料を探す

資料の場所はプロジェクトごとに違うので、決め打ちせずに探す。

1. `git ls-files` と、`docs/`・`design/`・`spec/`・`specs/`・ルートの `*.md` を一覧し、見出しと冒頭を読む。`node_modules/`、ビルドの出力、エンジンが生成するファイル（`.godot/`、`.import` など）、旧版のソース（解析用に置いた原作など）は読まない。
2. 各ファイルを、§2 のステップの成果物の候補に当てる。綴りの揺れ（例: `docs/conpect/`、`docs/conpetitor/`）や、似た名前（`game-design.md`、`systems.md`、`decisions.md`、`roadmap/`、`backlog`、`handovers/`）も候補にする。目安は次のとおり。

   | ステップ | 候補になる資料の例 |
   |---|---|
   | G1〜G3 | 企画書、`docs/concept/`、`README.md` のコンセプト、`project.md` |
   | G2 | 競合調査（`competitor*`、`surveys/`）、参考作品のメモ |
   | G4 | 前提・方針のメモ、`decisions.md`、仕様の前提の節 |
   | G5 | ゲームデザインの文書（`game-design.md`、`GDD`）のコンセプト・柱・ループの節 |
   | G6 | 検証の記録（`poc/`、`decision-log.md`、プレイテストのメモ） |
   | G7 | `systems.md`、経済・成長・戦闘式の文書、調整の手順（`gameConfig.md` など）、調整値のファイル |
   | G8 | `architecture.md`、`designs/architecture*`、`production/architecture*`、エンジンの設定（`project.godot`、`package.json`） |
   | G9 | `.specify/memory/constitution.md`、`CLAUDE.md` などの既存の規則 |
   | G10〜G12 | `docs/feature/`、`spec_order.md`、`specs/<NNN>/`、ロードマップ、バックログ |
   | G13 | UI の仕様、アートの方針、`docs/design/` |

3. 1 つの資料が複数のステップにまたがってよい（例: 1 本のゲームデザインの文書から G5 と G7 を作る）。

### 8.2 計画を作る

ステップごとに、次の 4 つのどれにするかを決め、根拠（候補の資料と、足りないもの）を付けて一覧にする。

| 扱い | 条件 | 動作 |
|---|---|---|
| 移し替える | 既存の資料に中身があり、gamekit の様式（テンプレートの見出しと表）にない | そのステップのスキルの更新モード（取り込み）で、資料を入力にして成果物を作る。足りない項目だけを質問（自動モードでは推奨案）で埋める |
| 完了として記録 | 既存の資料がすでに gamekit の成果物の場所と様式に合っている（例: speckit の `.specify/memory/constitution.md` にゲームの原則がそろっている） | 内容を確かめ、変更せずに §3 の形で記録する |
| 新しく作る | 候補の資料がない | そのステップのスキルを通常どおり実行する |
| 飛ばす | 開発が進んでいて、作っても後の工程で使わない（例: 実装が進んだプロジェクトの G3 の 3 案） | 記録せず、理由を完了報告に書く。G5 と G9 は飛ばせない（§6） |

既存の資料を尊重する規則:

- **G9（憲章）**: 憲章がすでにあれば、更新モードにする。§4 G9 の入力のうち、ゲームの原則（デザインの柱、数値はデータに置く、決定性、プレイ確認を `[人]` にする）が足りない分だけを、追記の案として示す。既存の条項の番号と文言は変えない。
- **G10〜G12（機能）**: `docs/feature/` と `specs/` がすでにあれば、既存の番号、スラッグ、`spec_order.md` の並びをそのまま使う。新しい機能は既存の最大の番号の次から振る。予約番号の `000`・`999` が別の名前で使われていれば（例: `000-app-basic`、`999-app-nfr`）、その名前のまま共通基盤・リリース基盤として扱い、`000-game-foundation`・`999-game-release` を新しく作らない。足りない要求は、その既存のファイルへの追記の案として示す。予約番号が別の機能に使われているときは、番号を振り直さず、共通基盤・リリース基盤の置き場所をユーザーに確かめる（自動モードでは、空いている番号を使わずに止まる）。
- **実装済みの機能**: `specs/<NNN>/tasks.md` がすべて完了している機能、または機能ファイルの状態欄が `完了`・`実装済み` の機能は、仕様を作り直さない。G7 の目標値（BT）を後から当てる場合は、その機能の `tuning.md` を `gamekit-balance` の spec モードで単独で作ることを、次の案内に書く。
- **既存の設計判断**: 既存の資料で決まっていること（エンジン、データの置き場所、セーブの形式など）は、gamekit の推奨と違っても既存を採る。変えた方がよい点は、`docs/auto-decisions.md`（対話モードでは完了報告）に「見直しの候補」として書くだけにし、勝手に変えない。
- **パス**: 既存の資料の置き場所に合わせて、`.gamekit/config.yaml` の `paths` を書き換えてよい（例: マスタデータが `game/content/` なら `paths.data: game/content`）。成果物を既定の場所に新しく作るか、既存のファイルを `paths` で指すかは、計画の一覧に書いて合意を取る。

### 8.3 合意と実行

- **対話モード**: 計画の一覧をユーザーに示し、AskUserQuestion で確かめる（ステップの数が多いので、扱いを変えたいステップだけを答えてもらう形でよい。推奨は一覧のとおり）。合意した計画を `docs/adopt-plan.md`（様式: [templates/adopt-plan.md](./templates/adopt-plan.md)）に書き、`docs(bootstrap): 取り込みの計画を作成` でコミットする（trailer なし）。
- **自動モード・一括質問モード**: 計画の推奨案をそのまま採り、`docs/adopt-plan.md` と `docs/auto-decisions.md` に記録する（「完了として記録」「飛ばす」にしたステップは、見直しの優先度を「中」にする）。
- 計画のあとは、§3 の再開の規則で G1 から順に進む。「完了として記録」のステップは内容を確かめて記録だけを作り、「飛ばす」のステップは記録しない。再開したときに `docs/adopt-plan.md` があれば、計画を作り直さずにそれに従う。
- G14 の検証では、既存の機能ファイルの様式の違い（speckit の様式など）で `validate.py` が出すエラーのうち、既存のファイルを書き換えないと直せないものは、エラーの一覧と直し方の案を完了報告に挙げ、ユーザーの合意を得てから直す（自動モードでは直さずに止まる）。

### 8.4 完了報告に足すもの

- ステップごとの扱い（移し替えた / 完了として記録した / 新しく作った / 飛ばした）と、移し替えた元の資料
- 既存の設計判断で、gamekit の推奨と違うまま残したもの（見直しの候補）
- 共通基盤・リリース基盤として扱った既存の機能（例: `000-app-basic`）
- 実装済みの機能に、後から `tuning.md` と目標値を当てるための案内
