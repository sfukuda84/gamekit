# gamekit-core スキル（G5: デザインの柱とコアループ）

ゲームの企画は、要素を足すほどぼやける。そこで、機能を考える前に **何を約束し、何を捨てるか（柱）** と、**プレイヤーが何を繰り返すか（コアループ）** を決める。以降の工程（プロトタイプ、システム、機能、レビュー）は、すべてこの 2 つを基準にする。

パスは `.gamekit/config.yaml` の `paths` で読み替える（既定は `docs/concept/`、`docs/game/`）。

## 1. 入力

- `docs/concept/premises.md`（GP1〜GP12。とくに GP1 コアファンタジー、GP4 コアループ、GP5 意思決定、GP6 progression、GP7 経済、GP8 失敗と再挑戦）
- `docs/concept/seed.md`、`docs/concept/direction.md`（選んだ方向性）
- `docs/research/competitors.md`（参考作品の評価・不満、ジャンルの定石）
- 引数の `--adopt <パス>`: 既存の企画書（例: `docs/specs/game-design.md`、`docs/design/systems.md`、`docs/concept/README.md`）

`premises.md` に、GP1・GP4・GP5 が「未決」のまま残っていれば、`gamekit-sparring` を案内して止まる。ユーザーが後で決めると明示した項目は、`[NEEDS CLARIFICATION: ...]` のまま進めてよい。

## 2. 手順

### ステップ 1: デザインの柱

1. GP1（コアファンタジー）と、選んだ方向性の「体験」から、約束する体験の候補を 5〜8 個挙げる。参考作品で評価されている点と、不満の点（`competitors.md`）も候補の材料にする。
2. 候補をまとめて 3〜5 本の柱にする。柱は次を満たすこと。
   - **判定に使える**: 「この機能は〇〇を強めるか」で、入れる・入れないを決められる。「楽しい」「快適」のように、どの機能にも当てはまるものは柱にしない。
   - **捨てるものがある**: 「やらないこと」を 1 つ以上書ける。ジャンルの定石（`competitors.md` の必須要素）を捨てるなら、その理由と、代わりに何で満たすかを書く。
   - **重なりが少ない**: 2 本の柱がいつも同じ答えを出すなら、1 本にまとめる。
3. 柱どうしがぶつかる場面（例: 「手軽さ」と「深い戦略」）を挙げ、どちらを優先するかを決める。
4. [templates/pillars.md](templates/pillars.md) の様式で `docs/game/pillars.md` に書く。

> 💬 柱の候補を、推奨の 3〜5 本と、捨てる候補に分けて示し、合意を取る（AskUserQuestion。最大 2 問）。

### ステップ 2: コアループ

1. GP4 から、ループを 1 文で書く（行動 → 報酬 → 強化・解放 → 次の挑戦）。
2. **3 つの層**に分ける。瞬間（秒: 操作と反応）、セッション（分: 1 回遊ぶ単位）、長期（時間・日: 成長と解放）。層ごとに、プレイヤーがすること、意思決定、報酬、対応する柱を書く。対応する柱がない層は、柱かループのどちらかが足りない。
3. **主要な意思決定**（D1〜）を書く。選択肢、何と何を天秤にかけるか、正解が状況で変わる理由。正解が 1 つに決まる選択は、意思決定ではなく支配戦略なので、条件を変えるか、意思決定から外す。
4. **資源の流れ**を概略で書く（資源ごとの入口・出口・ため込んだときに起きること）。詳しい数値は G7（`gamekit-systems`）で決める。
5. **失敗と再挑戦**（GP8）を書く。失うもの、残るもの、再挑戦までの時間。
6. ループの図を Mermaid で書く。
7. [templates/core-loop.md](templates/core-loop.md) の様式で `docs/game/core-loop.md` に書く。

### ステップ 3: 仮説

このループが面白いと言えるために正しくなければならないことを、**反証できる形**で書く（H1〜。3〜8 個）。

- 良い例: 「H2: 序盤の 10 分で、プレイヤーは 3 種類以上の作物を試したくなる。反証: 机上で、最も効率の良い作物だけを植え続ける方針が、ほかの方針より 30% 以上早く目標の所持金に届く」
- 悪い例: 「作物の育成が楽しい」（何が起きたら誤りか言えない）

各仮説に「確かめ方の案」を書く（机上のシミュレーション、紙のプロトタイプ、グレーボックスで人が遊ぶ、のどれか）。確かめるのは G6（`gamekit-prototype`）である。最も危うい仮説（外れたらループが成り立たないもの）を先頭に置く。

### ステップ 4: 点検

- すべての柱が、ループのどこかの層か意思決定に現れているか。現れない柱は、ループに足すか柱から外す。
- `premises.md` の GP10（最初の垂直スライス）で、ループの 3 層のうち少なくとも瞬間とセッションが遊べるか。
- 参考作品のループ（`competitors.md`）と比べて、差別化の仮説（`direction.md`）がループのどこに入っているか。入っていなければ、差別化はループの外の飾りになっている。

## 3. 出力と記録

| ファイル | 内容 |
|---|---|
| `docs/game/pillars.md` | デザインの柱（[templates/pillars.md](templates/pillars.md)） |
| `docs/game/core-loop.md` | コアループと仮説（[templates/core-loop.md](templates/core-loop.md)） |
| `docs/concept/backlog.md` | 柱から外して捨てたアイデア（追記） |

`gamekit-bootstrap` から呼ばれたときは、bootstrap がコミットする。単独で実行したときも同じ形で記録する（bootstrap の再開の判定に使うため）。

```bash
python3 <skills>/gamekit-status/scripts/gamekit.py checkpoint G5 "docs(bootstrap): G5 デザインの柱とコアループを定義" --allow-empty
```

更新モード・取り込みのときは、subject を `docs(game): デザインの柱とコアループを更新` にし、trailer を付けない（G5 の完了はすでに記録されている。まだ記録がない取り込みでは、上の形で記録する）。

## 4. 更新モード（`--update`）と取り込み（`--adopt`）

- **更新**: `pillars.md` か `core-loop.md` がすでにあるときは更新モードで動く。見直しの理由（プロトタイプの棄却、プレイ確認の結果、方向転換）を受け取り、変更の差分を示して合意を取ってから直す。直したら、影響を洗い出す。
  - 柱を変えたとき: `docs/feature/` の各機能の「関わる柱」、憲章（`.specify/memory/constitution.md`）の柱の条項、`docs/balance/targets.md` の根拠が柱のもの。影響の一覧を完了報告に書き、憲章の改訂は `speckit-constitution` を案内する（このスキルでは書き換えない）。
  - ループを変えたとき: 仮説の状態を「未検証」に戻すもの、`docs/game/systems.md`・`economy.md` の見直しが要る箇所。
  - 両ファイルの「変更の記録」に 1 行足す。
- **取り込み**: 既存の企画書を読み、柱とループに当たる記述を移し替える。元のファイルは動かさず、消さない。移し替えた記述には「出典: <元のファイル>§<節>」を添える。既存の記述に柱の「やらないこと」や仮説がなければ、ステップ 1〜3 で足す。

## 5. 自動モード（`--auto`）

`gamekit-bootstrap` の `--auto`・`--oneshot` から呼ばれたときは、bootstrap §7 の規則に従う。単独の `--auto` も同じ扱いにする。

| 論点 | 自動モードでの動作 |
|---|---|
| 柱の選択 | GP1 と方向性の体験に最も直接つながる 3 本を採る。捨てた候補は backlog に残す |
| 柱どうしの優先 | GP1（コアファンタジー）に近い柱を優先する |
| 仮説の選び方 | 外れたらループが成り立たないものから 3〜5 個 |
| 更新モードでの柱の変更 | 自動では行わない。変更案を書いて止まる（steering のモード: デザインの柱の変更が要るときは止まる） |

自動で決めたことは `docs/auto-decisions.md` の「G5」の節に書く。柱の選択は見直しの優先度を「高」にする。

## 6. 完了報告

- 柱の一覧（名前と判定の問い）と、捨てた候補
- コアループの 1 文と、3 層の要約、主要な意思決定の数
- 仮説の一覧（危うい順）と、確かめ方の案
- 点検で見つかった食い違いと、どう直したか
- 次の案内: `gamekit-prototype` で仮説を確かめる（bootstrap の中なら G6 に進む）

## 7. 規則

- 柱は少なく、強くする。5 本を超えたら、まとめるか捨てる。
- 柱に「やらないこと」がない、仮説に反証の条件がない状態で、完了にしない。
- 参考作品の柱やキャッチコピーを、そのまま使わない（steering の原則 8）。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
