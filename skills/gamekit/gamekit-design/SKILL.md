# gamekit-design スキル（見た目・画面・手触り → docs/design/ ＋ 機能ごとの ui.md）

デザインの要件を、性質の違う 4 つに分けて書く。`speckit-design` のゲーム版で、手触り（`FEEL.md`）を足してある。

| 出力 | 中身 | 作るとき | 使われ方 |
|---|---|---|---|
| `docs/design/DESIGN.md` | **見た目**の共通の決め事（アートディレクション、色、文字、レイアウトと余白、UI のコンポーネント、してよいこと・してはいけないこと） | 立ち上げ（`gamekit-bootstrap` の G13）か、このスキルの単独実行 | 憲章から参照され、各機能の `ui.md` と `plan.md` が従う |
| `docs/design/EXPERIENCE.md` | **画面と HUD** の共通の決め事（情報設計、画面一覧、画面遷移、状態のパターン、言葉づかい、言語とローカライズ、アクセシビリティ） | 同上 | 同上。steering の言語ルールの「ゲームの中の文言」が参照する |
| `docs/design/FEEL.md` | **手触り**の共通の決め事（入力と応答、フィードバック（演出と音）、カメラと視点、難しさと手応え、プレイ確認の観点） | 同上 | `ui.md`、`tasks.md` の `[人]` のプレイ確認、`gamekit-review` の Feel 軸が参照する |
| `docs/design/tokens.tokens.json` | UI の色、文字、余白、演出の長さなどの**値の正本**（DTCG 2025.10）。テーマは `tokens.<テーマ>.tokens.json` | 同上 | 実装はトークンから値を使う |
| `specs/<NNN-name>/ui.md` | **機能ごとの画面仕様**（画面・HUD と要件の対応、画面ごとの表示と操作、演出とフィードバック、文言、プレイ確認の観点） | `gamekit-feature` の S4-1（§3） | `plan.md`、`tasks.md`、実装、レビューが参照する |

正本はツールに依存しない Markdown と JSON で持つ。Claude Design は案を見比べて選ぶための任意の道具であり（§4）、決めたことは必ず正本に書き戻す。

パスは `.gamekit/config.yaml` の `paths` で読み替える（以下は既定のパス）。

## 0. 大原則

- **正本は `docs/design/` と `ui.md` である。** Claude Design のアーティファクトは URL を残すだけにする。
- **値はトークンかマスタデータにだけ書く。** UI の色、文字、余白、演出の長さはトークンに、ゲームの調整値（攻撃の強さ、ヒットストップの長さを調整値として扱う場合など）はマスタデータと `tuning.md` に置く。`DESIGN.md`・`FEEL.md`・`ui.md` には値を書かず、トークン名（`color.ui.accent`、`motion.duration.short` など）で参照する。
- **技術を書かない。** エンジンのノードやライブラリは `docs/architecture.md` と各機能の `plan.md` で決める。
- **柱に従う。** アートのトーンと手触りの方針は、デザインの柱（`docs/game/pillars.md`）と対応づける。柱に反する演出（「テンポを最優先」の柱なのに長い演出を挟むなど）を共通の決め事にしない。
- **アクセシビリティとローカライズの水準は `docs/nfr.md` に従う。** `NFR-UX` を `EXPERIENCE.md` と `FEEL.md` の最低線にする。違う水準が要る場合は、`gamekit-nfr` の更新モードで先に見直す。
- **手触りは人が確かめる。** `FEEL.md` の「プレイ確認の観点」は、実機でのプレイ確認（`[人]`）で使う。AI のレビューだけで手触りを合格にしない。
- **オマージュ元の見た目を持ち込まない。** 参考作品の固有のキャラクター、ロゴ、UI の意匠、色の組み合わせをそのまま使わない（steering の原則 8）。
- **推測で埋めない。** アートの方向など、作り手しか知らないことは質問する。自動モードでは推奨案を仮定として採用し、記録する（§6）。
- **書き出す前に合意を取る。**
- ドキュメントは日本語で書く。

`docs/design/` がすでにある場合は、**更新モード**として §5 に従う。

## 2. 共通の決め事を作る（立ち上げ、単独実行）

### ステップ 1: 読み込みと対象の判定

入力を読み、次を整理する。

- **画面の有無**: 画面のない構成（サーバーだけ、ツールだけ）なら、ステップ 5 で `DESIGN.md` を「**対象**: UI なし」として理由だけを書き、ステップ 7 と 8 だけを行って終える（憲章への条項は足さない）。`EXPERIENCE.md`、`FEEL.md`、トークンは作らない。
- **遊ぶ場面と端末**: 端末（PC、携帯機、スマートフォン、ブラウザ）、操作（ゲームパッド、マウス、タッチ）、1 回の長さ
- **画面の候補**: 各機能の主な要求から、主な画面と HUD を拾う。共通の画面（タイトル、ポーズ、設定、セーブ・ロード）は 000 から拾う
- **演出の候補**: コアループの各層で起きる出来事（当たる、取る、増える、失う、達成する）
- **決まっていること**: `NFR-UX` の水準と言語、`NFR-PF` の入力の遅れの上限

### ステップ 2: ヒアリング

次の論点のうち、入力から決まらないものを AskUserQuestion で聞く。1 ラウンド最大 4 問、推奨案を先頭に置く。

| 順 | 論点 | 書く場所 |
|---|---|---|
| 1 | トーン（3 語以内）と、参考にする作品・しない作品 | `DESIGN.md` の「アートディレクション」 |
| 2 | アートの形式（ドット絵、2D の手描き、3D）と、素材の作り方（自作、外注、有料の素材） | 同上 |
| 3 | 主な端末と操作（ゲームパッド中心か、マウスか、タッチか） | 「レイアウトと余白」、`EXPERIENCE.md` の「操作の基本」 |
| 4 | 手触りの方向（例: 重く手応えがある / 軽くテンポがよい / 静かで落ち着く） | `FEEL.md` の「フィードバック」「入力と応答」 |
| 5 | 演出の量と、飛ばせるか | `FEEL.md` の「フィードバック」 |
| 6 | テーマ（暗い UI だけか、明るい UI もか） | 「色」、`tokens.<テーマ>.tokens.json` |
| 7 | システムの文言の文体 | `EXPERIENCE.md` の「言葉づかい」 |

推奨案は、柱と参考作品から判断できる最も無難な案にする。

`--with-mock` のときは、ヒアリングの後に §4 の手順で案を作り、選んでもらってからステップ 3 に進む。

### ステップ 3: 画面一覧・演出・観点の整理

- 主な画面と HUD に ID を振る。形は `SCR-<機能番号 3 桁>-<連番 2 桁>`。機能番号は `docs/feature/` のファイル名の先頭の番号である（例: `001-core-combat.md` の HUD は `SCR-001-01`）。状態は「構想」にする。
- 主な遷移（タイトル → プレイ → ポーズ、失敗 → やり直し）を決める。
- コアループの主な出来事ごとに、見た目・音・揺れと止めの方針を決め、`FEEL.md` の「フィードバック」の表にする。
- プレイ確認の観点（`FEEL-NNN`）を 3〜8 個決める。柱ごとに、柱が守られているかを確かめる観点を 1 つ以上入れる。

### ステップ 4: 書き出し案の提示と合意

次をまとめて示し、承認を得る。

1. アートディレクション、主要な色と文字の方針（`--with-mock` なら選んだ案）
2. 画面一覧（ID、画面、機能、種類）と主な遷移
3. 手触りの方針（入力と応答、主な演出、難しさの感じ方）とプレイ確認の観点
4. 状態のパターン、言語とローカライズ、アクセシビリティの最低線
5. 憲章に足す条項（ステップ 6）

### ステップ 5: 書き出し

- `docs/design/DESIGN.md`、`EXPERIENCE.md`、`FEEL.md`、`tokens.tokens.json` を、それぞれのテンプレートに沿って書く。テンプレートの例の値は、決めた内容に置き換える。
- トークンは DTCG 2025.10 の形で書く。
  - 色は `{"colorSpace": "srgb", "components": [r, g, b], "hex": "#rrggbb"}`、大きさは `{"value": 数値, "unit": "px"}`（または `rem`）、演出の長さは `{"value": 数値, "unit": "ms"}`（`duration`）にする。
  - 役割のトークン（`color.focus` など）は、基本の色を `{color.ui.accent}` の形で参照する。
  - テーマは `tokens.<テーマ>.tokens.json` に、基本のファイルにあるトークンの上書きだけを書く。
- 文字と背景のコントラストが水準（AA なら 4.5:1）を満たす色にし、組み合わせと比を `DESIGN.md` の「色」に書く。
- エンジンがトークンを直接読めない場合（Godot の Theme など）の変換は、000 の `plan.md` で決める。ここでは書かない。

### ステップ 6: 憲章への反映

憲章に `docs/design/` を参照する条項がなければ、`speckit-constitution` の手順で改訂として足す。条項の例:

- 画面か HUD を持つ機能は、`docs/design/DESIGN.md`・`EXPERIENCE.md`・`FEEL.md` に従い、画面仕様（`specs/<NNN-name>/ui.md`）を `plan.md` より先に作る。この条項を足す前に仕様化した機能には、さかのぼって求めない。
- UI の色、文字、余白、演出の長さは `docs/design/` のトークンから使い、実装に値を直接書かない。
- 手触りの関わる機能は、`tasks.md` の最後に `FEEL.md` の観点による実機でのプレイ確認（`[人]`）を置く。

「UI なし」のときは、条項を足さない。

### ステップ 7: 検証

```bash
python3 <skills>/gamekit-design/scripts/validate_design.py docs/design
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。`python3` がない環境では `python` または `py -3` に読み替える。エラーが 0 件になるまで直す。

### ステップ 8: 報告と記録

- 作成したファイルと、画面一覧の件数（機能ごと）、プレイ確認の観点の件数
- アートディレクション、主な端末と操作、手触りの方向、アクセシビリティと言語の水準
- `--with-mock` のとき: モックの URL、採用した案と理由。作れなかったときは、その理由
- 憲章に足した条項
- 次の手順の案内（G14。`gamekit-bootstrap` の中で実行している場合は、その手順に戻る。単独なら `gamekit-all` で各機能の仕様化へ）

最後に §1 の形で G13 を記録する。

## 3. 機能ごとの画面仕様（`gamekit-feature` の S4-1）

`gamekit-feature` の S4-1 から、`WORKTREE_DIR` の中で実行する。`FEATURE_DIR` は `specs/<FEATURE_NAME>` である。

1. **対象の判定**: 次のどれかなら、`FEATURE_DIR/ui.md` を「**対象**: UI なし」にして理由を 1 行書き、手順 5 に進む。
   - `docs/design/DESIGN.md` が「UI なし」
   - この機能の要件（`spec.md` の FR）に、プレイヤーが見る画面、HUD、演出がない（データの読み込み、シミュレーション、サーバーの処理だけ、など）

   `docs/design/` がないプロジェクト（デザインの工程を足す前に立ち上げたもの、取り込んだもの）で、画面のある機能は、`ui.md` を「UI あり」のまま、共通の決め事を参照せずに書く（コンポーネントは一般的な名前で書き、プレイ確認の観点は ID を付けずに書く）。完了報告で、`gamekit-design` を単独で実行して共通の決め事を作ることを案内する。
2. **下書き**: [templates/ui.md](./templates/ui.md) に沿って、`spec.md` のユーザーストーリーと要件から画面と HUD を起こす。
   - 画面 ID は `SCR-<この機能の番号>-<連番>`。`EXPERIENCE.md` の画面一覧にこの機能の画面が「構想」として挙がっていれば、その ID を使う。
   - 各画面の「対応する要件」に FR の番号を書く。画面を伴う FR は、どれかの画面か演出に対応させる。
   - 表示、操作（アクション名とゲームパッドのフォーカス）、状態、使うコンポーネント、端末による違い、アクセシビリティを書く。共通の決め事と同じことは書かず、違う点だけを書く。
   - 「演出とフィードバック」に、この機能の出来事ごとの見た目・音・揺れと止めを書く（`FEEL.md` と違う点だけ。強さと長さの値は書かない。調整値なら S4-2 の `tuning.md` で、UI の値ならトークンで決める）。
   - 「文言」に、文言のキーと既定の言語の文言を書く（文言はマスタデータか翻訳ファイルに置く）。
   - 「プレイ確認の観点」に、`FEEL.md` の観点（`FEEL-NNN`）から、この機能で見るものを選び、どう確かめるかを書く。機能に固有の観点は ID なしで足す。S6 の `tasks.md` の `[人]` のプレイ確認のタスクがここを参照する。
3. **確認**: 画面の構成や、要件の読み方で判断が要る点を、推奨案を添えて質問する（最大 3 問）。`--auto`（`gamekit-worktree` §6）なら推奨案を採用し、`FEATURE_DIR/auto-decisions.md` に記録する。
   - `--with-mock` のときは、§4 の手順で主な画面のモックを作り、案を選んでもらう。選んだ案の URL を `ui.md` のヘッダの「モック」に書き、決まったことを本文に反映する。
4. **反映**:
   - 画面を作るうえで `spec.md` の要件の不足や矛盾に気づいたら、`spec.md` も直す（`## Clarifications` に `### Session YYYY-MM-DD (UI)` として記録する）。
   - `docs/design/EXPERIENCE.md` の画面一覧で、この機能の行を足すか直し、状態を「仕様化済み」にする。ほかの機能の行、「最終更新」、「変更履歴」は変えない（機能どうしのマージの競合を減らすため）。
   - 新しい共通のコンポーネント、状態のパターン、演出の方針、プレイ確認の観点が要る場合は、`DESIGN.md`・`EXPERIENCE.md`・`FEEL.md` に足し、「変更履歴」に書く。トークンの追加も同じにする。既存のトークンや決め事を変える必要がある場合は、自動では変えず、ユーザーに確かめる（自動モードでは止まる。§6）。
5. **検証**:

   ```bash
   python3 <skills>/gamekit-design/scripts/validate_design.py docs/design --feature specs/<FEATURE_NAME>
   ```

   エラーが 0 件になるまで直す。警告（画面に対応しない FR など）は、画面を伴わない要件なら残してよい。`docs/design/` がない場合の警告も残してよい。
6. `gamekit-feature` に戻り、`checkpoint <FEATURE_NAME> S4-1` を記録する。

## 4. Claude Design でモックを作る（`--with-mock`）

`--with-mock` のときだけ行う。決めたことは、必ず `docs/design/` か `ui.md` に書き戻す。

### 使えるかどうかの判定

次をすべて満たすときに使う。満たさないときは、モックを作らずにテキストの仕様だけで進め、理由を完了報告と `DESIGN.md` の「参照したモック」（機能では `ui.md` のヘッダ）に書く。止まらない。

- Claude Code で動いている（ほかのエージェントには `/design` がない）
- `/design` を使える。呼び出してエラーになったら、使えないものとして扱う
- Claude Code のクラウドセッション（`CLAUDE_CODE_REMOTE=true`）では使えないことがある。試してエラーになったら、テキストの仕様で進める

モックは UI と HUD の配置と見た目を比べるためのもので、ゲームの絵（キャラクター、背景）やアニメーションの代わりにはならない。消費が大きいので、立ち上げでは代表の画面 1 つ（多くはプレイ中の HUD かメインのメニュー）、機能では主な画面 1〜2 枚に絞る。

### 立ち上げ（§2 ステップ 2 の後）

1. ヒアリングの結果から、代表の画面を 1 つ選ぶ。
2. `/design` に次の依頼文を渡し、方向性の違う案を 2〜3 個、1 つのキャンバスに並べて作る。
   - ゲームの概要、トーン、参考にする作品（固有の見た目は持ち込まないと明記する）、主な端末と操作、基準の解像度、テーマ
   - 画面の目的と、表示する主な情報（ダミーの数値でよい。ゲームの画面の部分は灰色の箱でよい）
   - 案ごとの違い（例: 案 A は情報を画面の端に寄せる、案 B は必要なときだけ出す）
3. 公開された URL を示し、AskUserQuestion で案を選んでもらう（推奨案を先頭に置く）。
4. 選んだ案から、色、文字、余白、コンポーネントの形を読み取り、トークンと `DESIGN.md` に書き戻す。「参照したモック」に URL、採用した案、採用しなかった案と理由を書く。

### 機能（§3 手順 3）

1. `ui.md` の下書きから、主な画面を 1〜2 枚選ぶ。
2. `/design` に、`ui.md` の該当する画面の仕様と、`DESIGN.md` の決め事を渡して作る。案は 1〜2 個にする。
3. URL を示し、採用する案と直す点を確かめる。URL を `ui.md` のヘッダの「モック」に書き、決まったことを本文に反映する。

`/design-sync`（実装したコンポーネントの取り込み）は React のデザインシステムが対象である。`docs/architecture.md` のエンジンが Web（React）でなければ案内しない。案内する場合も、ユーザーが始めるコマンドであり、このスキルからは実行しない。

## 5. 更新モード

- `docs/design/` を変えるときは、差分と影響（すでに `ui.md` を作った機能、実装済みの機能で変わること）を示し、合意した変更だけを反映する。各文書の「変更履歴」に日付、内容、理由を足す。
- トークンの名前は変えない（実装が参照している）。役割が変わった場合は新しい名前を足し、古い名前に `$deprecated` を付ける。
- 機能の `ui.md` は、その機能の仕様工程（`gamekit-feature`）の中で直す。マージ済みの機能の画面を変える場合は、その機能の `spec.md` と `ui.md` を直す変更として扱う。
- **既存のプロジェクトへの取り込み**: speckit の `docs/design/`（`ブランドとトーン` の節、Web 向けの画面一覧）や、既存の UI の資料（例: srpg の `docs/specs/ui/`）がある場合は、元のファイルを動かさずに読み、gamekit の様式に移し替える案を示す。足りない `FEEL.md` と、`EXPERIENCE.md` の「言語とローカライズ」を足す。診断には `validate_design.py docs/design --lenient`（エラーを警告に落とす）を使い、移し替えた後は `--lenient` なしでエラーを 0 件にする。

## 6. 自動モード（`--auto`）

| 論点 | 自動モードでの動作 |
|---|---|
| §2 のヒアリング | 入力から推奨案を作って採用する。根拠がなければ、柱に合うトーン、`docs/architecture.md` の対象端末に合う操作、暗い UI のみ、演出は短く飛ばせる、システムの文言は です・ます調、言語は `docs/nfr.md` のとおり、を採る |
| §2 の書き出し案の合意 | 提示せずにそのまま書き出す。内容は完了報告に載せる |
| §3 の確認 | 推奨案を採用する |
| §4 の案の選択 | 入力と最もよく合う案を採用する。直す点は求めない |
| 既存のトークンや決め事の変更（§3 手順 4） | 自動では変えずに止まる |

自動で決めたことは、立ち上げでは `docs/auto-decisions.md` に、機能では `FEATURE_DIR/auto-decisions.md` に記録する（`gamekit-bootstrap` §7、`gamekit-worktree` §6 の書き方に従う）。アートディレクション、主な端末と操作、手触りの方向は、見直しの優先度を「高」にする。

## 7. 禁止事項

- `DESIGN.md`・`FEEL.md`・`ui.md` に、色、大きさ、長さ、調整値の値を直接書くこと（トークン名で参照するか、マスタデータに置く）
- Claude Design のアーティファクトだけに決めたことを残し、正本に書き戻さないこと
- `ui.md` に技術（エンジンのノード、ライブラリ）を書くこと
- 手触りを AI のレビューだけで合格にすること
- オマージュ元の固有の見た目（キャラクター、ロゴ、UI の意匠）を、そのまま共通の決め事や画面に入れること
- ユーザーの合意なしに `docs/design/` を書き出す、または上書きすること（自動モードを除く）
- `/design-sync` をユーザーの指示なしに実行すること
