# gamekit-foundation スキル（共通基盤 → 000-game-foundation）

ゲームの中身（遊び）以外の共通の仕組みの要件を、1 つの機能概要 `docs/feature/000-game-foundation.md` にまとめる。`000` は予約番号であり、すべての機能より先に仕様化・実装する。`speckit-common-feature` のゲーム版である。

パスは `.gamekit/config.yaml` の `paths` で読み替える（以下は既定のパス）。

## 0. 大原則

- **遊びを持ち込まない。** ここに入れるのは、どのゲームでもほぼ同じ形で要る仕組みだけである。ルール、ユニット、アイテム、このゲームに固有の画面は、それぞれの機能に残す。
- **技術選定はしない。** 方式は `docs/architecture.md` に従う。ここでは「何ができればよいか」を書く。
- **AI が確かめられる基盤にする。** マスタデータの検証、乱数のシードの固定、ヘッドレスでの起動、デバッグ用の数値の表示は、後のテストとバランスのシミュレーション（`gamekit-balance`）の前提になる。垂直スライスに必ず入れる。
- **根拠のないものは入れない。** 根拠にしてよいのは、`docs/feature/premises.md` の「基盤の候補」、各機能の要求、`docs/architecture.md`、`docs/concept/premises.md` の GP、ユーザーの回答である。
- **書き出す前に合意を取る。** 自動モード（`--auto`）では §6 の規則で決めて記録する。
- **記述の粒度は `gamekit-features` と同じ**（広く浅く）。クラス名、データの項目、具体的な数値は書かない。
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

| 入力 | 用途 |
|---|---|
| `docs/feature/premises.md` の「基盤の候補」（振り先が 000） | 000 に入れる候補と、必要とする機能 |
| `docs/feature/*.md`、`README.md`、`spec_order.md` | 各機能の要求と依存 |
| `docs/architecture.md` | セーブ、データ、乱数、入力、ローカライズ、テストの方式 |
| `docs/concept/premises.md` | GP2（遊ぶ場面。中断の多さ）、GP3（操作）、GP8（失敗と再挑戦。セーブの方式に効く） |
| `.specify/memory/constitution.md` | 憲章の原則 |

| 出力 | 内容 |
|---|---|
| `docs/feature/000-game-foundation.md` | 共通基盤の機能概要。様式は [`gamekit-features` の templates/feature.md](../gamekit-features/templates/feature.md)（「プレイヤー体験」と「関わるシステムと目標値」の節は省いてよい） |
| `docs/feature/README.md` | 一覧の先頭に 000 の行を足す |
| `docs/feature/spec_order.md` | 先頭に `- **0. [<名称>](./000-game-foundation.md)**: <一言>` を足す |
| 各機能ファイル（状態が「未着手」のもの） | `**依存**` に `000-game-foundation` を足す |
| `docs/feature/premises.md` | 「基盤の候補」の各行の「結果」を書く |

終わったら、`gamekit-bootstrap` §3 のコマンドで G11 を記録する（`python3 <skills>/gamekit-status/scripts/gamekit.py checkpoint G11 "docs(bootstrap): G11 共通基盤を定義" --allow-empty`）。単独で実行したときも記録する。更新モードで 000 を直しただけのときは、`docs(feature): 000 を更新` の通常のコミットにする。

**`docs/feature/` にすでに `000-*` がある場合**（`000-game-foundation.md` のほか、speckit の `000-app-basic.md` など）は、新しく作らず、その名前のまま**更新モード**（§4）で使う。以下の `000-game-foundation` は、その名前に読み替える。`000-*` が複数あるときは、どれを共通基盤にするかをユーザーに確かめる（自動モードでは止まる）。

## 2. 手順

### ステップ 1: 候補の洗い出し

「基盤の候補」と各機能の要求から候補を洗い出し、次の一覧で漏れがないかも確かめる。

| 区分 | 候補 |
|---|---|
| ゲームループ | 起動、タイトル、シーンの遷移と読み込み中の表示、一時停止、ゲームの終了 |
| 時間 | 固定のタイムステップ、ゲーム内の時間の進め方と止め方（一時停止、早送り） |
| 入力 | 操作の抽象化（アクション名）、キーボード・ゲームパッド・タッチ、割り当ての変更 |
| セーブ | セーブとロード、スロット、自動セーブ、中断と再開（アプリの中断を含む）、セーブのバージョンと古いセーブの読み込み、壊れたセーブの扱い |
| データ | マスタデータの読み込み、起動時の検証（型と範囲）、検証に失敗したときの扱い |
| 乱数 | シード付きの乱数、シードの記録（再現とリプレイ）、シミュレーションでの固定 |
| 設定 | 音量、画面（解像度、全画面）、文字の大きさ、言語、設定の保存 |
| ローカライズ | 文言の置き場所と切り替え、文字の長さが変わったときの扱い（文言そのものは各機能） |
| 音 | BGM と効果音の再生の仕組み、音量の分類 |
| デバッグ | ログ、開発用の表示（数値、当たり判定）、チート（時間を進める、資源を足す）、ヘッドレスでの起動 |
| 計測（任意） | 遊ばれ方の記録（送るなら同意と送り先。999 と相談） |
| オンライン（ある場合） | アカウント、クラウドセーブ、接続が切れたときの扱い |

### ステップ 2: 範囲のヒアリング

AskUserQuestion で、候補ごとに「垂直スライスで入れる / MVP までに入れる / 後で入れる / 入れない」を決める。1 ラウンド最大 4 問、推奨案を先頭に置く。

- 各機能の要求から必要と判断できるものは、根拠（機能名）を添えて推奨する。
- データの検証、シード付きの乱数、ヘッドレスでの起動、最低限のデバッグ表示は「垂直スライスで入れる」を推奨する（§0）。
- 「後で入れる」ものは `docs/concept/backlog.md` の候補に足す（様式は `gamekit-features` の templates/backlog.md）。
- 「MVP までに入れる」ものが多い場合は、ステップ 3 で分ける。

### ステップ 3: 大きさの確認

000 は `/speckit-specify` に 1 回で渡せる大きさにする（P1 のユーザーストーリーが 1〜3 本）。

- 大きすぎる場合は、垂直スライスに要るもの（ゲームループ、入力、データの読み込みと検証、乱数、セーブの最小形、デバッグの最小形）だけを 000 に残し、残り（設定の画面、ローカライズの切り替え、割り当ての変更など）は通常の番号の機能（既存の最大値の次から。区分は MVP）に分ける。分けた機能は `000-game-foundation` に依存させる。
- 分け方を示し、合意を取る。

### ステップ 4: 書き出し案の提示と合意

次をまとめて示し、承認を得る。

1. 000 の主な要求（区分ごと）
2. スコープ外にするもの（後で入れるもの、入れないもの、各機能に残すもの）
3. 依存に `000-game-foundation` を足す機能の一覧
4. 分けた機能がある場合は、その一覧

### ステップ 5: 書き出し

- `000-game-foundation.md` を書く。ヘッダは `**状態**: 未着手 | **区分**: 垂直スライス | **想定順序**: 0 | **依存**: —` とする（区分は、`docs/feature/` のいちばん前の区分にする）。H1 は「ゲームの基盤」など、ゲームに合った日本語名にする。
- 「前提・設計原則との関係」に、`docs/architecture.md` の該当節（セーブ、データ、乱数、テスト）を書く。
- 「/speckit-specify に渡す記述案」を書く。ユーザーストーリーは開発者とプレイヤーの両方の視点でよい（例: 「開発者として、同じシードで同じ結果を再現したい」）。
- `README.md`、`spec_order.md`、各機能の依存、`docs/feature/premises.md` の「基盤の候補」の結果を、§1 の表どおりに更新する。状態が `spec化済み` 以降の機能は変更せず、影響があれば報告する。

### ステップ 6: 検証

```bash
python3 <skills>/gamekit-features/scripts/validate.py docs/feature
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。エラーが 0 件になるまで直す。000 に依存していない機能の警告は、意図どおりなら理由を報告に書く。

### ステップ 7: 報告と記録

- 000 に入れた仕組みと、スコープ外にしたもの
- 更新したファイルと、依存を足した機能
- 検証の結果
- 次の手順の案内（G12 `gamekit-nfr`。`gamekit-bootstrap` の中で実行している場合は、その手順に戻る）

最後に §1 の形で G11 を記録する。

## 3. 記述の規則

- 仕組みの「どう作るか」（クラス、シーン、データの形式）は書かない。`docs/architecture.md` と 000 の `plan.md` で決める。
- セーブの中身（何を保存するか）は各機能が決める。000 では「セーブに項目を足せる仕組みと、バージョンを上げて古いセーブを読める仕組み」までを書く。
- 各機能が 000 の何を使うかは、各機能の「前提・設計原則との関係」に書き足してよい（状態が「未着手」のものに限る）。

## 4. 更新モード

`000-*` がすでにある場合は、次のように進める。

- 状態が「未着手」なら、§2 ステップ 1 の一覧で足りないものを洗い出し、追加・変更の差分案を示して、承認されたものだけ反映する。speckit の `000-app-basic.md` のように Web サービス向けの要求（ログイン、メール送信など）が中心なら、ゲームに要るものを足す案と、要らないものをスコープ外に移す案を示す（消さない）。
- 状態が `spec化済み` 以降なら、000 は書き換えない。足りないものは、通常の番号の新しい機能として提案する。
- ゲーム向けの節（「プレイヤー体験」「関わるシステムと目標値」）は、000 では足さなくてよい。

## 5. 既存のプロジェクト

既存のコードに、すでにセーブや入力などの仕組みがある場合は、000 の状態を `実装済み（spec なし）` か `一部実装（spec なし）` にし、「現状の実装」節にコードの場所と、§2 ステップ 1 の一覧との差を書く。

## 6. 自動モード（`--auto`）

| 論点 | 自動モードでの動作 |
|---|---|
| 範囲のヒアリング | 各機能の要求から必要と判断できるものと、§0 の「AI が確かめられる基盤」を垂直スライスに入れる。それ以外は MVP の別の機能に分けるか、「後で入れる」として backlog に足す |
| 分け方、書き出しの合意 | 推奨案のまま進める |
| `000-*` が複数ある | 止まる |

自動で決めたことは `docs/auto-decisions.md` に記録する（`gamekit-bootstrap` §7 の書き方）。

## 7. 禁止事項

- 遊び（ルール、ユニット、アイテム、ゲームに固有の画面）を 000 に入れること
- 技術選定を 000 に書くこと（`docs/architecture.md` に従う）
- ユーザーの合意なしに書き出す、または上書きすること（自動モードを除く）
- 状態が `spec化済み` 以降の機能ファイルを書き換えること
- 既存の機能の番号を振り直すこと、既存の `000-*` を消す・名前を変えること
