# gamekit-nfr スキル（非機能要件 → docs/nfr.md ＋ 999-game-release）

非機能要件を、性質の違う 2 つに分けて書く。`speckit-nfr-feature` のゲーム版である。

| 出力 | 中身 | 使われ方 |
|---|---|---|
| `docs/nfr.md` | **横断要件**。全機能が守る目標と基準（フレームレート、セーブの互換、決定性、アクセシビリティなど） | 憲章から参照され、各機能の `spec.md` と `plan.md` が従う。`gamekit-review` の Standards 軸と Feel 軸が確かめる |
| `docs/feature/999-game-release.md` | **リリース基盤**。実装が必要な仕組み（CI、書き出しとビルド、配布、クラッシュの記録、ストアの準備） | 通常の機能と同じく `gamekit-all` などで仕様化・実装する |

`999` は予約番号である。ほかの機能は 999 に依存しない。

パスは `.gamekit/config.yaml` の `paths` で読み替える（以下は既定のパス）。

## 0. 大原則

- **構成で達成できる目標にする。** 目標値は `docs/architecture.md` のエンジン、言語、対象端末で達成できる水準にする（例: Godot 4 の C# で Web は対象にできない）。構成を変えないと達成できない目標を求められたら、その旨と `gamekit-architecture` の見直しを提案する。
- **垂直スライス時と公開時に分ける。** 垂直スライスの段階で公開時の水準を求めない。
- **測れる形で書く。** 「軽快に」「快適に」ではなく、数値、条件、確認方法を書く。ヘッドレスでは測れないもの（フレームレート、入力の遅れ、見た目）は、確認方法を実機での確認（`[人]`）にする。
- **手触りの水準は FEEL.md に渡す。** 入力の遅れの上限やアクセシビリティの水準はここで決め、具体的な演出や観点は `gamekit-design`（G13）の `FEEL.md` と `EXPERIENCE.md` で決める。
- **書き出す前に合意を取る。** 自動モード（`--auto`）では §5 の規則で決めて記録する。
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

| 入力 | 用途 |
|---|---|
| `docs/architecture.md` | エンジン、対象端末、データとセーブの方式、テストとビルドのコマンド、見直しの条件 |
| `.gamekit/config.yaml` | `commands`（CI で回すもの） |
| `.specify/memory/constitution.md` | 憲章の原則 |
| `docs/feature/000-*.md` | 共通基盤の範囲（セーブ、データの検証、設定など） |
| `docs/feature/premises.md` | 「基盤の候補」（振り先が 999） |
| `docs/concept/premises.md` | GP2（遊ぶ場面）、GP3（端末と操作）、GP10（公開の形）、GP11（収益化） |
| `docs/feature/*.md`、`docs/game/systems.md` | 性能やデータ量に効く要求（同時に動く物体、シミュレーションの規模） |

| 出力 | 様式 |
|---|---|
| `docs/nfr.md` | [templates/nfr.md](./templates/nfr.md) |
| `docs/feature/999-game-release.md` | [`gamekit-features` の templates/feature.md](../gamekit-features/templates/feature.md)（「プレイヤー体験」と「関わるシステムと目標値」の節は省いてよい） |
| `docs/feature/README.md`、`spec_order.md` | 999 の行を足す |
| `docs/feature/premises.md` | 「基盤の候補」（振り先が 999）の「結果」を書く |
| `.specify/memory/constitution.md` | `docs/nfr.md` を参照する条項がなければ、`speckit-constitution` の手順で足す |

終わったら、`gamekit-bootstrap` §3 のコマンドで G12 を記録する（`python3 <skills>/gamekit-status/scripts/gamekit.py checkpoint G12 "docs(bootstrap): G12 非機能要件とリリース基盤を定義" --allow-empty`）。単独で実行したときも記録する。更新モードで直しただけのときは、`docs(nfr): <変更の要約>` の通常のコミットにする。

`docs/nfr.md` か `999-*` がすでにある場合は、**更新モード**として §4 に従う。**`docs/feature/` にすでに `999-*` がある場合**（`999-game-release.md` のほか、speckit の `999-app-nfr.md` など）は、新しく作らず、その名前のまま使う。以下の `999-game-release` は、その名前に読み替える。`999-*` が複数あるときは、どれをリリース基盤にするかをユーザーに確かめる（自動モードでは止まる）。

## 2. 手順

### ステップ 1: 読み込み

入力を読み、次を整理する。

- 構成の制約（エンジンと言語で書き出せる端末、ヘッドレスで確かめられる範囲）
- 処理の重さ（同時に動く物体、シミュレーションの規模、読み込むデータの量）
- 遊ばれ方（1 回の長さ、中断の多さ、オンラインの有無）
- 公開の形（体験版、早期アクセス、正式版）と配布先（Steam、App Store、Google Play、Web、itch.io など）

### ステップ 2: ヒアリング

次の区分ごとに、決まっていない目標を AskUserQuestion で聞く。1 ラウンド最大 4 問、推奨案を先頭に置く。推奨案は、構成で達成できる値にする。

| 区分 | ID の接頭辞 | 決めること（例） |
|---|---|---|
| 対応端末と性能 | `NFR-PF` | 下限の端末、フレームレート、読み込み時間、メモリ、入力の遅れの上限 |
| セーブとデータ | `NFR-DA` | セーブの互換を保つ時期、セーブが失われないこと、マスタデータの検証 |
| 決定性とテスト | `NFR-QA` | 決定性の範囲、自動テストの範囲（単体、ヘッドレス、シミュレーション）、クラッシュの基準 |
| アクセシビリティとローカライズ | `NFR-UX` | 操作の割り当ての変更、文字の大きさ、色覚、字幕、言語、難しさの調整 |
| セキュリティとプライバシー | `NFR-SE` | 秘密情報（署名鍵、API キー）の管理、遊ばれ方の記録と送信、不正への耐性（オンライン） |
| 法令・規約・ライセンス | `NFR-CO` | ストアの規約と年齢区分、アセットとフォントのライセンス、有料の要素の法令 |
| コスト | `NFR-CT` | サーバーやサービスの月額の上限 |

- 000 と重なる項目（セーブ、データの検証）は、000 を機能の要求とし、`docs/nfr.md` には基準（互換を保つ期間など）だけを書く。
- CI の最小形（テストの自動実行）を早く入れたい場合は、000 が「未着手」なら 000 の要求に足すか、999 で扱うかを質問する。

### ステップ 3: 横断要件とリリース基盤への仕分け

- **横断要件（`docs/nfr.md`）**: 各機能が作るときに守る基準。例: 「下限の端末で 60 fps」「同じシードで同じ結果」「色だけで情報を伝えない」
- **リリース基盤（`999-game-release.md`）**: 1 回作れば全体に効く仕組み。例:
  - CI: `commands` の `test`・`lint`・`run_headless`・`balance_sim` を、push や PR のたびに回す。バランスのシミュレーションの結果（`gamekit-balance check`）を CI で確かめる
  - 書き出しとビルド: 対象の端末ごとの書き出しの設定、版の番号の付け方、ビルドの成果物の置き場所
  - 配布: ストアへのアップロードの手順、体験版の作り方（`[人]` のタスクを含む。アカウント、審査、価格、公開の判断）
  - クラッシュの記録: クラッシュとエラーのログを集める仕組み（送るなら同意）
  - ストアの準備: ストアのページの素材（スクリーンショット、紹介文、トレーラー）の一覧（作るのは `[人]`）
  - クレジットとライセンスの表示

### ステップ 4: 書き出し案の提示と合意

次をまとめて示し、承認を得る。

1. `docs/nfr.md` の要件の一覧（ID、区分、垂直スライス時の値、公開時の値、確認方法）
2. `999-game-release.md` の主な要求と、そのうち `[人]` になる作業
3. 999 を `spec_order.md` のどこに置くか。既定は **MVP の最後の機能の後、拡張の機能の前**（公開の前に要るため）。CI だけ先に要る場合は、000 に足すか、999 を前に置くかを相談する（依存の順序は守る）。
4. 今の構成では達成できない目標（あれば）と、その対応

### ステップ 5: 書き出し

- `docs/nfr.md` を [templates/nfr.md](./templates/nfr.md) に沿って書く。テンプレートの区分のうち、対象外のもの（オンラインがないときの不正への耐性など）は「対象外」と書いて残す。
- `999-game-release.md` を書く。ヘッダは `**状態**: 未着手 | **区分**: MVP | **想定順序**: 999 | **依存**: 000-game-foundation`（000 がなければ `—`）とする。「前提・設計原則との関係」に `docs/nfr.md` の対応する ID を書く。
- `README.md` の一覧と `spec_order.md` に 999 の行を足し、`docs/feature/premises.md` の「基盤の候補」の結果を書く。
- 憲章に `docs/nfr.md` を参照する条項がなければ、`speckit-constitution` の手順で足す（例: 「すべての機能は docs/nfr.md の横断要件を満たす。plan.md の憲章チェックで確かめる」）。

### ステップ 6: 検証

```bash
python3 <skills>/gamekit-features/scripts/validate.py docs/feature
```

`<skills>` は、このスキルが置かれた skills ディレクトリである。エラーが 0 件になるまで直す。

### ステップ 7: 報告と記録

- `docs/nfr.md` の要件の件数（区分ごと）と、主な目標値
- `999-game-release.md` の主な要求、`[人]` の作業、`spec_order.md` での位置
- 今の構成では達成できない目標（あれば）と、その対応
- 次の手順の案内（G13 `gamekit-design`。`gamekit-bootstrap` の中で実行している場合は、その手順に戻る）

最後に §1 の形で G12 を記録する。

## 3. 記述の規則

- `docs/nfr.md` の各要件には、ID、垂直スライス時の値、公開時の値、確認方法を書く。確認方法が実機でのプレイだけのものは「（[人]）」と書く。
- 999 には、仕組みの「何ができればよいか」を書き、使うサービスやツールは `docs/architecture.md` に従う。
- 各機能に固有の性能要件（特定の場面の物体の数など）は、その機能の `spec.md` で決める。`docs/nfr.md` には全体の既定値を書く。

## 4. 更新モード

- `docs/nfr.md` を変えるときは、差分と影響（すでに `spec化済み` 以降の機能が新しい基準を満たすか）を示し、合意した変更だけを反映する。「変更履歴」に日付、内容、理由を足す。speckit の `docs/nfr.md`（Web サービス向けの稼働率など）を取り込んだ場合は、ゲームに要る区分（NFR-PF、NFR-QA など）を足す案と、当てはまらない要件を「対象外」にする案を示す（消さない）。
- `999-*` が `spec化済み` 以降なら書き換えない。足りないものは、通常の番号の新しい機能として提案する。

## 5. 自動モード（`--auto`）

| 論点 | 自動モードでの動作 |
|---|---|
| 目標値 | エンジンと対象端末で達成できる推奨値を採る。根拠がなければ、PC は 60 fps、モバイルは 30 fps を下限、セーブの互換は公開時から、決定性はロジックの範囲、言語は日本語のみ |
| CI を 000 と 999 のどちらで扱うか | 999 で扱う（000 が「未着手」でも、自動では足さない） |
| 999 の位置、書き出しの合意 | 既定（MVP の最後）にし、推奨案のまま進める |
| `999-*` が複数ある | 止まる |

自動で決めたことは `docs/auto-decisions.md` に記録する（`gamekit-bootstrap` §7 の書き方）。対応端末と下限の性能は、見直しの優先度を「高」にする。

## 6. 禁止事項

- 構成で達成できない目標を、注記なしに書くこと
- 測れない形（「軽快に」「十分に」など）で要件を書くこと
- ヘッドレスで測れないものを、自動テストで確かめたように書くこと
- ユーザーの合意なしに書き出す、または上書きすること（自動モードを除く）
- 状態が `spec化済み` 以降の機能ファイルを書き換えること、既存の `999-*` を消す・名前を変えること
