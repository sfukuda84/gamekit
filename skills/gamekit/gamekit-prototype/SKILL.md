# gamekit-prototype スキル（G6: コアループの検証）

steering の原則 1「面白さを先に確かめる」を担う。機能を作り込んだ後にコアループの欠陥が見つかると、作ったものの多くを捨てることになる。ここでは、**反証できる仮説を、いちばん安い方法で、判定の基準を先に決めてから**確かめる。

机上の検証で確かめられるのは、数値の性質（速さ、偏り、支配戦略、インフレ）と、ルールの穴までである。迷う楽しさや手触りは人が遊ばないと分からない。AI が「面白い」と判定しない。

パスは `.gamekit/config.yaml` の `paths` で読み替える（既定は `docs/game/`）。

## 1. 入力

- `docs/game/core-loop.md`（仮説 H1〜、3 層、意思決定、資源の流れ）
- `docs/game/pillars.md`、`docs/concept/premises.md`（GP2 遊ぶ場面、GP4〜GP8）
- `docs/research/competitors.md`（参考作品の数値。比較の基準に使う）
- 引数の仮説の ID（なければ、状態が「未検証」か「保留」のすべて）

`core-loop.md` に反証の条件のない仮説があれば、その仮説は書き直してから計画する（書き直しは `gamekit-core` の規則に従う。短い修正ならこのスキルで直し、`core-loop.md` の「変更の記録」に書く）。

## 2. 手順

### ステップ 1: 計画

[templates/plan.md](templates/plan.md) の様式で `docs/game/prototype/plan.md` を書く。仮説ごとに次を決める。

1. **方法**: 下の表から、仮説を判定できるうちで最も安いものを選ぶ。

   | 方法 | 向いている仮説 | 実行 |
   |---|---|---|
   | 机上シミュレーション | 数値の性質（何分で届くか、どの選択が強すぎるか、資源が余るか） | AI が Python で書いて回す |
   | 机上プレイ | ルールの穴、手順の多さ、詰み | AI が手順どおりに数ターン進め、盤面と選択を記録する |
   | 紙のプロトタイプ | 意思決定の面白さ、読み合い | 人が遊ぶ（`[人]`）。AI は手順、カード、記録用紙を用意する |
   | グレーボックス | 操作の手触り、テンポ、カメラ | 人が作るか、G8 の後に最小のシーンを作って人が遊ぶ（`[人]`） |

2. **判定の基準**: 実施の前に、支持と棄却の基準を数値か観察で決める。`core-loop.md` の反証の条件を、測れる形に直す（例: 「最短方針が、ほかの方針より 30% 以上早く 1,000 ゴールドに届いたら棄却」）。実施の後に基準を動かさない。
3. **担当**: AI か人か。人の方法しかない仮説は、手順を用意して「保留（人のプレイ待ち）」にする。

> 💬 方法と判定の基準を示し、合意を取る（とくに、人が遊ぶ方法を選んだ仮説）。

### ステップ 2: 机上シミュレーション

1. [templates/loop_sim.py](templates/loop_sim.py) をもとに、`docs/game/prototype/sim/<仮説の ID>-<名前>.py` を書く。
   - パラメータは `PARAMS` にまとめ、値ごとに根拠を書く。根拠のない値は「仮」と書く。参考作品の値を使うときは、`competitors.md` の出典を書く。
   - 方針（シミュレーションのプレイヤー）を 2 つ以上用意する。最低でも「最も効率の良い選択を繰り返す方針」と「選択を散らす方針」を比べる（支配戦略の検出）。
   - シードを固定し、試行を 100 回以上にする。平均だけでなく、下位・上位 10% も見る。
   - モデルにしなかったもの（操作の上手さ、演出、学習）を、スクリプトの冒頭と plan.md に書く。
2. 実行して、結果の表を `results.md` に貼る。
3. パラメータを少し動かして（±20% など）、判定が変わらないかを確かめる（感度）。少し動かしただけで判定が変わるなら、判定は「保留」にし、そのパラメータを G7 で慎重に決める対象として書く。

### ステップ 3: 机上プレイと紙のプロトタイプ

- **机上プレイ（AI）**: ルールを箇条書きにし、AI が 1 人のプレイヤーとして 3〜5 ターン（またはセッション 1 回分）進める。各ターンの状態、選べた選択肢、選んだもの、迷ったかどうかを記録する。選択肢が 1 つしか意味を持たない場面、手順が多すぎる場面、詰む場面を探す。
- **紙のプロトタイプ（人）**: 用意するもの（カード、盤面、早見表）、1 回の流れ、記録してほしいこと（迷った場面、退屈な場面、同じ選択を繰り返した回数）を `plan.md` に書き、印刷できる形の資料を `docs/game/prototype/paper/` に置く。結果は人から受け取って `results.md` に書き写す。

### ステップ 4: 判定と逆流

[templates/results.md](templates/results.md) の様式で `docs/game/prototype/results.md` に書く。仮説ごとに **支持 / 棄却 / 保留** を決め、根拠（数値・観察）を書く。

- **支持**: `core-loop.md` の仮説の状態を「支持（机上）」にする。机上の方法で支持しても、人のプレイ確認が要るものは、その旨を書く。
- **棄却**: ループか柱に欠陥がある。
  1. 原因を書く（どの意思決定が崩れたか、どの資源が余ったか）。
  2. `core-loop.md`（必要なら `pillars.md`）の直し方の案を作り、合意を取って直す（`gamekit-core` の更新モードの規則）。直した箇所を両方の「変更の記録」と `results.md` の「逆流の記録」に書く。
  3. 直した版で、同じ仮説を同じ判定の基準で確かめ直す。
  4. **同じ仮説が 2 回続けて棄却されたら止まる。** 直し方の候補（ループを変える / 柱を変える / 仮説を捨てて別の差別化を探す）と推奨案を示して、ユーザーに判断を仰ぐ。自動モードでも止まる。
- **保留**: 判定できなかった理由と、確かめる時期と方法（例: 「001 の実装後に `[人]` のプレイ確認で」）を書く。保留の仮説は、G10（`gamekit-features`）で関わる機能の受入基準か、`[人]` のタスクにつなぐ。

### ステップ 5: G7 への引き継ぎ

シミュレーションで使ったパラメータと、わかった性質（例: 「強化の値段の伸びが 1.5 倍を超えると、30 分で 2 回しか強化できない」）を、`results.md` の「わかったこと」にまとめる。G7（`gamekit-systems`）は、これを `economy.md`・`progression.md` の初期値と目標値の材料にする。

## 3. 出力と記録

| ファイル | 内容 |
|---|---|
| `docs/game/prototype/plan.md` | 仮説ごとの方法と判定の基準 |
| `docs/game/prototype/results.md` | 判定、根拠、逆流の記録 |
| `docs/game/prototype/sim/*.py` | 机上シミュレーション（コミットする。結果を再現できるように） |
| `docs/game/prototype/paper/` | 紙のプロトタイプの資料（人が遊ぶとき） |
| `docs/game/core-loop.md`、`pillars.md` | 仮説の状態、逆流での修正 |

`gamekit-bootstrap` から呼ばれたときは、bootstrap がコミットする。単独で実行したときも同じ形で記録する。

```bash
python3 <skills>/gamekit-status/scripts/gamekit.py checkpoint G6 "docs(bootstrap): G6 コアループの仮説を検証" --allow-empty
```

G6 の完了の条件は、すべての仮説が「支持」か「保留（確かめる時期と方法つき）」であることである。「棄却」が残っている間は完了にしない。G6 の後に追加で確かめたときは、subject を `docs(game): 仮説 H<n> を検証` にし、trailer を付けない。

## 4. 自動モード（`--auto`）

`gamekit-bootstrap` の `--auto`・`--oneshot` から呼ばれたときは、bootstrap §7 の規則に従う。単独の `--auto` も同じ扱いにする。

| 論点 | 自動モードでの動作 |
|---|---|
| 方法と判定の基準 | 推奨案を採用する。判定の基準は、参考作品の値か、GP2（遊ぶ場面）から導く |
| 人が遊ぶ方法しかない仮説 | 資料を用意して「保留（人のプレイ待ち）」にし、見直しの優先度を「高」にする |
| 1 回目の棄却 | 推奨の直し方で `core-loop.md` を直し、確かめ直す。柱（`pillars.md`）の変更が要る直し方は採らず、止まる |
| 同じ仮説の 2 回続けての棄却 | 止まる（ステップ 4） |

自動で決めたことは `docs/auto-decisions.md` の「G6」の節に書く。

## 5. 完了報告

- 仮説ごとの判定（支持 / 棄却 / 保留）と根拠の要約
- 逆流させた修正（`core-loop.md`・`pillars.md` のどこを変えたか）
- 保留の仮説と、確かめる時期と方法（人のプレイが要るもの）
- G7 に引き継ぐパラメータと性質
- 次の案内: `gamekit-systems`（bootstrap の中なら G7 に進む）

## 6. 規則

- 判定の基準を、結果を見てから変えない。変えるなら、仮説を書き直して確かめ直す。
- シミュレーションの結果だけで「面白い」と書かない。書けるのは、数値の性質についての支持・棄却までである。
- 机上シミュレーションの式は、後でゲーム本体に移す前提で書かない（使い捨てでよい）。ゲーム本体のシミュレーションは `gamekit-balance` §5 で、本体の処理を呼ぶ形で作り直す。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
