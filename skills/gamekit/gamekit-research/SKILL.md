# gamekit-research スキル（G2: 参考作品の調査）

方向性を決める前に、ジャンルの「地図」を作る。ここで集めたものは**方向性の案（G3）と壁打ち（G4）の材料**であり、ゲームの決定ではない。

パスは `.gamekit/config.yaml` の `paths` で読み替える。進捗の記録とモードは [`gamekit-bootstrap`](../gamekit-bootstrap/SKILL.md) の §3・§7 に従う。

## 0. 大原則

- **出典のない事実を書かない。** 作品の仕組み、売上、価格、レビューの傾向、ストアの規約には、出典 URL と参照日を付ける。
- **AI が挙げた作品名は、1 件ずつ実在を確かめる。** 存在しない作品や、開発元・発売年・仕組みの取り違えが起きやすい。ストアのページ（Steam、App Store、Google Play、各コンソールのストア）、開発元・発売元の公式ページ、ゲームのデータベース（MobyGames、IGDB など）、百科事典のどれかに当たれたものだけを載せる。当たれなかったものは「未確認」の表に分け、根拠にしない。
- **仕組みの細部を記憶で断言しない。** 数値（成長の速さ、価格、確率）や仕様の細部は、攻略 Wiki、公式のパッチノート、開発者のインタビュー・講演（GDC など）で確かめる。確かめられなかったものは「未確認」と書く。
- **ページを開けない出典**: 取得が拒否されるサイト（403）や、動的に描かれるストアのページは、検索結果の要約か、SteamDB などの集計サイトで確かめ、その旨を出典の欄に書く。検索の要約は固有名詞を取り違えることがあるので、要約だけで確かめた固有名詞は、別の出典でもう一度確かめる。
- **売上・プレイヤー数の推定値**（SteamDB のレビュー数からの推定など）は、推定であることと推定の方法を書く。
- **調べたが見つからなかったこと**は、それ自体を記録する（「〜を組み合わせた作品は、検索語 ○○・○○ では見つからなかった（参照日）」）。見つからないことが「空いている席」の根拠になる。ただし、見つからないことは存在しないことの証明ではない。
- **既存の記述は消さない。** 再実行したときは、日付つきの新しい節を足す。
- **オマージュ元を特別に扱う。** `seed.md` にオマージュ元があれば、受け継ぎたいもの（仕組み・雰囲気・テーマ）と、持ち込んではいけないもの（固有名詞、用語、キャラクター、テキスト、アセット、特徴的な仕組みの組み合わせ）を分けて書く。これは後の Originality 軸（`gamekit-review`）の照合の対象になる。法的な判断はしない。疑わしいものは「人か専門家が確かめる」と書く。

## 1. 入力

- `docs/concept/seed.md`（原文、コアファンタジー、ピッチ、参考作品・オマージュ元の候補、調査の論点、選択）
- 引数の追加の観点や作品名
- 既存の `docs/research/competitors.md`（あれば、重複を避ける）
- 既存のプロジェクトに取り込んだとき: 既存の競合調査の資料（`docs/conpetitor/`、`backlogs/competitor-analysis*`、`surveys/` など）。中身を読み、確かめ直したうえで移し替える。元の資料は動かさず、出典として書く。

`seed.md` がなければ `gamekit-seed` を案内する。

## 2. 手順

### ステップ 1: 調査計画

`seed.md` の「調査の論点」と選んだピッチから、次の 5 つの調査の問いを作り、`competitors.md` の冒頭に書く。

| 系統 | 調べること |
|---|---|
| A. 参考作品 | 同じジャンル・同じコアファンタジー・同じ繰り返す行為を持つ作品。オマージュ元を含める |
| B. ジャンルの定石 | このジャンルのプレイヤーが期待する必須要素と、よく使われる仕組み（コアループ、成長、経済、失敗の扱い） |
| C. プレイヤーの評価 | ストアのレビュー、コミュニティで評価されている点と不満点（とくに中盤で飽きる・終盤がない・作業になる、などの傾向） |
| D. 市場と規模 | 価格帯、開発の体制と期間、プラットフォーム、販売の傾向（推定） |
| E. IP とプラットフォームの事情 | オマージュ元の固有の要素、ストアの規約（AI 生成のコンテンツの開示など。実行のたびに公式で確かめる） |

### ステップ 2: 参考作品（A）

- **件数の目安**: 5〜10 本。ジャンルの定番 2〜3 本、最近（おおむね 5 年以内）の小〜中規模の作品 3〜5 本、隣接ジャンルで同じコアファンタジーを持つ作品 1〜2 本。オマージュ元は件数に含めず、別に置く。
- **比較に向く作品を優先する。** 同じくらいの規模（少人数・インディー）の作品を優先する。超大作は「誰もが知る原型」として別の表に置く。
- 各作品について、次を記録する。
  - 題名、開発元・発売元、プラットフォーム、発売年、価格
  - 出典と参照日
  - コアループ（秒・分・時間の 3 層で、分かる範囲）
  - progression（成長と解放の仕組み）
  - 経済（主な資源と、その入口と出口）
  - 失敗と再挑戦の扱い
  - 評価されている点、不満点（ストアのレビュー・比較記事から。出典つき）
  - 規模の目安（開発の人数・期間、遊べる時間。分かる範囲。推定ならその旨）
  - 本作との重なり（コアファンタジー／繰り返す行為／舞台とトーン／progression の型）
- **重なりが大きい作品には印を付ける。** 上の 4 つの観点のうち 2 つ以上が重なる作品を「重なりが大きい」とする。重なりが大きい作品は、G3 で「差のつけ方」を必ず検討し、機能ごとの Originality 軸で照合する対象にする。

### ステップ 3: ジャンルの定石（B）

- このジャンルで「ないと検討から外される」必須要素を挙げる（例: ライフシムの季節と曜日、ローグライトの周回ごとの恒久的な強化）。各要素に、採用している参考作品を添える。
- よく使われる仕組みを 5〜15 個挙げ、各仕組みの典型と、参考作品での扱い方（そのまま／ひねる／外す／使わない）を書く。単に逆にしただけの「外し」は、差別化として数えない。

### ステップ 4: プレイヤーの評価（C）

- ストアのレビュー（Steam の最も参考になったレビュー、App Store・Google Play の低評価のレビュー）、コミュニティ、比較記事から、評価と不満の傾向をまとめる。出典つき。
- 不満は、どのループの層（秒・分・時間）で起きているかに当てる。G5 のコアループの設計と、G7 の経済・成長曲線の設計の材料にする。

### ステップ 5: 市場と規模（D）

- 参考作品の価格帯、プラットフォーム、開発の体制、販売の傾向を表にする。推定値は推定の方法を書く。
- 本作の想定の規模（`seed.md` の「規模が見える」）と比べ、現実的かを 1〜3 行で書く。

### ステップ 6: IP とプラットフォームの事情（E）

- オマージュ元ごとに、「受け継ぐもの」と「持ち込まないもの」の表を作る。持ち込まないものには、固有名詞、用語、キャラクター、台詞やテキスト、音楽・画像、特徴的な仕組みの組み合わせ（複数の仕組みがその作品と同じ組み合わせで並ぶこと）を含める。
- 対象のプラットフォームのストアの規約のうち、企画に効くもの（AI 生成のコンテンツの開示、課金と確率の表示、年齢区分など）を、公式のページで確かめて書く。

### ステップ 7: まとめる

1. A〜E で集めた事実を、1 件 1 行のラベルにし、似たものをグループにして見出しを付ける（KJ 法）。
2. 最後に、次をそれぞれ 3 行以内で書く。
   - **このジャンルのプレイヤーが求めているもの**
   - **まだ空いている席**（参考作品が扱っていない組み合わせ、解消されていない不満）
   - **差別化の仮説**（本作は何で選ばれるか。G3・G5 で検証の対象にする）

### ステップ 8: 種への影響

調査で、種（`seed.md`）のピッチや前提を揺るがす発見（例: 同じピッチの有名作がある、想定の規模が参考作品よりずっと大きい、ストアの規約に当たる）があれば、「種への影響」の節に書く。G3 は、この節を最初に読んで案を作る。

### ステップ 9: 提示

`competitors.md` を書き、要点（空いている席、差別化の仮説、重なりが大きい作品、IP の注意点）をユーザーに示す。

- **対話モード**: 追加で調べたい観点や作品を聞く（「このままで G3 へ」を推奨案にする）。追加があれば、ステップ 2〜7 を足してから終える。
- **自動モード**: 追加の調査はしない。重なりが大きい作品と IP の注意点を `docs/auto-decisions.md` に記録する（見直しの優先度: 中。オマージュ元の「持ち込まないもの」は「高」）。サブエージェントとして呼ばれたときは、記録すべき判断を最終回答で返し、記録は親が行う。

作品ごとの詳しいメモが長くなるときは、`docs/research/competitors/<slug>.md` に分けてよい（`competitors.md` の表から相対リンクを張る）。

## 3. 出力

- `docs/research/competitors.md`（様式: [templates/competitors.md](./templates/competitors.md)）
- 任意で `docs/research/competitors/<slug>.md`

Web を調べられない環境では、推測で埋めない。調べるべき項目と理由を「未調査」として書き、ユーザーに伝える。自動モードでは、その項目の見直しの優先度を「高」にする。

終わったら `gamekit-bootstrap` §3 のコマンド（`python3 <skills>/gamekit-status/scripts/gamekit.py checkpoint G2 "<subject>" --allow-empty`）で `G2` を記録する（単独で実行したときも記録する）。

## 4. 完了報告

- 参考作品の件数（確認済み / 未確認）と、重なりが大きい作品
- ジャンルの定石（必須要素）の要約
- プレイヤーが求めているもの、まだ空いている席、差別化の仮説
- オマージュ元ごとの「持ち込まないもの」の要約
- 次の案内: `gamekit-direction`（G3）
