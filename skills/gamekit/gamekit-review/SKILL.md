# gamekit-review スキル（5 軸のレビュー）

ゲームの変更差分を、**5 つの独立した軸**で審査し、直す。片方の軸を満たしても別の軸で破綻する変更（仕様どおりだが毎フレーム割り当てて重い、規約どおりだが数値が直書きで調整できない、動くが参考作品の固有の仕組みをそのまま写している）を防ぐため、軸ごとに分けて見る。

外部の CLI には依存しない。エージェント自身のコード探索、テストの実行、Web 検索（Originality 軸）、サブエージェント（独立審査）で完結する。パスは既定の配置で書いている。`.gamekit/config.yaml` の `paths` で読み替える。

## 1. 引数

```text
$ARGUMENTS
```

- 対象の指定は §3 の表に従う。
- `--axis <軸,...>` で軸を絞る（既定は 5 軸すべて）。数値だけの変更なら `--axis balance,spec` などにしてよい。
- `--round <n>` はレビューの回（`gamekit-coding` の S10 が 1、S11 が 2）。記録のファイル名と、2 回目のレンズに使う。単独で呼ばれたときは省略してよい。

## 2. 5 つの軸

### 軸 A: Standards（エンジンの作法・性能・決定性・品質）

**共通**

- **毎フレームの処理**: `_process`・`_physics_process`・`requestAnimationFrame`・`Update` などの毎フレーム呼ばれる処理での割り当て（配列・辞書・文字列の結合・クロージャの生成）、全件の探索、ノードやコンポーネントの検索（名前やパスでの取得）。キャッシュするか、イベントで動かす。
- **決定性**: 乱数をシード付きの生成器から取っているか（グローバルの乱数・`Math.random()`・時刻に依存していないか）。ゲームのロジックが描画のフレームレートに依存していないか（固定の時間刻み、`delta` の扱い）。辞書・集合の列挙順に結果が依存していないか。
- **状態と寿命**: 解放されたオブジェクトへの参照、シグナル・イベントの購読の解除漏れ、シーンの切り替えで残るタイマーや非同期処理。
- **セーブ**: 足した状態がセーブ・ロードの対象になっているか。セーブデータのバージョンと移行（`000-game-foundation` の仕組み）に乗っているか。
- **型安全とエラー処理**: 型の欠落、`null` の扱い、マスタデータの読み込みの失敗（欠けたキー、型の違い）を検出しているか。例外や失敗を握りつぶしていないか。
- **コードの匂い**: 重複、肥大化した神クラス・オートロード、他のシステムの内部に立ち入る処理（Feature Envy）、ドメインの概念の生の値の乱用（座標・ID・通貨を素の数値で扱う）、仕様にない先回りの抽象化。
- **秘密情報**: API キー、署名鍵、ストアの資格情報の混入。

**Godot（`engine: godot`）**

- GDScript は静的型（`var hp: int`、戻り値の型）を付けているか。`@onready` と `get_node` のパスの壊れやすさ（`%UniqueName` やエクスポート変数で受けるか）。
- シグナルの接続をコードとシーンの二重で行っていないか。`connect` の解除、`queue_free` 後の参照。
- オートロード（シングルトン）に状態を集めすぎていないか。テストからロジックを呼べるか（ノードに依存しないクラスに分けているか）。
- `Resource`（`.tres`）を共有して書き換えていないか（`duplicate()` の要否）。`.tscn`・`.tres` をテキストで書いたときの `uid`・`ext_resource` の参照の整合。
- `_physics_process` と `_process` の使い分け、物理の処理を `_process` で行っていないか。
- C#（`language: csharp`）では、毎フレームの LINQ・ボクシング、`GodotObject` の寿命、`Variant` の変換、PublishAot 時のリフレクションの使用。
- ヘッドレス実行（`commands.run_headless`）でエラーと警告が出ないか。

**Web（`engine: web`）**

- 描画ループと状態更新の分離（React などでは、ゲームの状態を毎フレーム再描画のきっかけにしていないか。ref やストアの外で回すか）。
- `setInterval`・`setTimeout` に依存した時間の進み、タブが裏に回ったときの扱い（`visibilitychange`）。
- 描画のコスト（不要な再レンダリング、Canvas・WebGL の状態の作り直し、画像の再読み込み）。
- セーブ（`localStorage`・IndexedDB）の容量、例外（容量超過、プライベートモード）、改ざんへの姿勢（`docs/architecture.md` の方針どおりか）。
- TypeScript の `any` の乱用、マスタデータの型（スキーマと型の一致）。

`engine: other` のときは、`docs/architecture.md` の言語とフレームワークの作法で見る。

### 軸 B: Spec（仕様・設計・柱との整合）

- `spec.md` の機能要件（FR-xxx）とユーザーストーリーの受入基準を満たしているか。実装漏れ、エッジケース（`spec.md` の Clarifications の Round 2）の放置がないか。
- `ui.md` の画面・HUD・状態・演出のとおりか。表示の値は `docs/design/` のトークンから使っているか。
- `tuning.md` の調整値が、書かれたデータの場所にあり、コードがそこから読んでいるか。
- `plan.md`、`data-model.md`、`contracts/` の設計契約（シグナル、イベント、データのスキーマ）に忠実か。
- 憲章（`.specify/memory/constitution.md`）とデザインの柱（`docs/game/pillars.md`）に反していないか。柱の「やらないこと」に当たる挙動が混ざっていないか。
- 仕様にない機能・挙動が混ざっていないか（スコープクリープ）。

### 軸 C: Balance（数値・経済・支配戦略）

- **直書き**: 遊びに効く数値（ダメージ、価格、確率、時間、上限、経験値）がコードに直書きされていないか。`tuning.md` にない数値で遊びに効くものは、`tuning.md` とマスタデータに移す。
- **目標値**: `python3 <skills>/gamekit-balance/scripts/balance.py check --feature <FEATURE_NAME>` が通るか（結果がなければ、`run` してから）。基準値がある場合は `diff` で、この変更が既存の指標を大きく動かしていないか。
- **支配戦略と抜け道**: 常に最善になる選択肢、無限に稼げる手順（売買の差益、再出現の稼ぎ、セーブとロードのやり直し）、進めなくなる状態（ソフトロック）、0 除算や上限の突破。
- **経済**: 資源の入口（source）と出口（sink）が `docs/game/economy.md` の想定どおりに釣り合うか。長時間遊んだときにインフレ・デフレしないか。
- **成長と難しさ**: 成長曲線（`docs/game/progression.md`）から外れた急な段差、序盤の詰まり、終盤の作業化。
- 数値の妥当性を AI の感覚だけで断じない。式、シミュレーションの結果、参考作品の実例（出典付き）を根拠にする。根拠がないものは「プレイ確認で判定」として `[人]` のタスクの観点に回す。

### 軸 D: Feel（手触り・読みやすさ・アクセシビリティ）

`docs/design/FEEL.md` と `EXPERIENCE.md` の決め事を基準にする。

- **入力の応答**: 入力から反応までの遅れ（フレーム数）、入力の先行受付・猶予（コヨーテタイムなど、`FEEL.md` で決めたもの）、連打と長押しの扱い。
- **フィードバック**: 行動の結果が、絵・音・振動・数値の表示で分かるか（ヒットストップ、画面の揺れ、効果音の有無）。成功と失敗の区別がつくか。
- **読みやすさ**: 状態（体力、残り時間、選べる行動）が一目で分かるか。重要な情報が演出に埋もれていないか。文言が長くなっても崩れないか（ローカライズ）。
- **難しさの感じ方**: 失敗の理由がプレイヤーに分かるか（理不尽に感じないか）。救済と再挑戦までの時間。
- **アクセシビリティ**: 色だけに頼らない表示、字幕、文字の大きさ、操作の変更、点滅（`EXPERIENCE.md` の水準）。
- コードから判定できるもの（遅れのフレーム数、演出の有無、色だけの表示）は直す。体感の判定が要るもの（気持ちよさ、難しさの感じ方）は、AI が合格にしない。`[人]` のプレイ確認のタスクに観点として足し、指摘の状態を「プレイ確認へ」にする。

### 軸 E: Originality（参考作品との類似）

`docs/research/competitors.md` の参考作品（とくにオマージュ元）と、`docs/concept/premises.md` の GP12（IP・オマージュの境界）を基準にする。

- **名前と用語**: キャラクター・アイテム・技・地名・システムの名前が、参考作品の固有名詞と一致または酷似していないか。
- **テキスト**: 台詞、説明文、UI の文言に、参考作品の特徴的な文がそのまま入っていないか。特徴的な文（10〜20 字以上の固有の言い回し）を Web で検索して確かめる。
- **アセット**: 画像・音・フォント・アイコンの出所とライセンス。参考作品のアセットや、ライセンスの不明な素材が入っていないか（`[人]` の確認が要るものはタスクにする）。
- **仕組みの組み合わせ**: ひとつひとつのルールはジャンルの共有財産であることが多い。問題になりやすいのは、特徴的な仕組みの**組み合わせ**と、その見せ方（画面の構成、演出、数値の体系）までが一致すること。組み合わせのうち、どれが共通の定石で、どれが参考作品の固有のものかを分けて書く。
- Web 検索ができない環境では、軸の結果を「未確認」と書き、確かめる項目を残す。AI の判定は一次のふるい分けであり、「類似の疑い」は人か専門家が確かめる（steering の原則 8）。断定的に「問題なし」と書かない。

## 3. レビュー対象の特定

| 指定 | 差分コマンド | 主な用途 |
|---|---|---|
| 直近のコミット | `git diff HEAD~1` | S11 の修正差分 |
| ブランチ全体 | `git diff main...HEAD` | 機能のブランチ全体（マージ先が main 以外なら読み替える） |
| 未コミットの変更 | `git diff` または `git diff --cached` | 作業中の差分 |
| パス | `git diff <range> -- <path>` | 特定のファイル・ディレクトリ |
| 引数なし | ブランチの差分があれば `main...HEAD`、なければ `HEAD~1` | 自動判別 |

マスタデータ（`paths.data` の下）、シーン・リソースのテキストファイル、翻訳ファイルの差分も対象に含める。バイナリのアセットは、追加・変更されたファイルの一覧と出所を見る。

対象のフィーチャーは、ブランチ名（`feature/<NNN-name>`）、`.specify/feature.json`、または引数から決める。フィーチャーに属さない差分（機能の工程の外）では、Spec 軸は憲章と柱と関係する `docs/` で見る。

## 4. 手順

### 4.1 文脈の読み込み

1. 差分（変更されたファイルと行）を取得する。
2. 関係する文書を読む: `spec.md`、`ui.md`、`tuning.md`、`plan.md`、`data-model.md`、`contracts/`、`balance-report.md`、憲章、`docs/game/pillars.md`、`economy.md`、`progression.md`、`docs/balance/targets.md`、`docs/design/FEEL.md`、`EXPERIENCE.md`、`docs/research/competitors.md`、`docs/concept/premises.md`、`docs/architecture.md`。
3. `.gamekit/config.yaml` の `engine` と `language` を読み、Standards 軸のエンジン別の観点を選ぶ。

### 4.2 独立審査（サブエージェント）

サブエージェント（Claude Code の Agent など）が使えるときは、軸ごとに 1 つずつ、**会話の文脈を持たない**サブエージェントに審査させる。実装した本人の思い込みを持ち込まないためである。

- 渡すもの: 軸の名前と §2 のその軸の観点、差分の範囲（コマンド）、読むべき文書のパス、エンジン、出力の形式（§5 の指摘の形）。「落とす理由を探す」立場で審査させ、指摘ごとに根拠（ファイルと行、文書の該当箇所、検索結果の URL）を必ず付けさせる。
- 渡さないもの: 実装の経緯、親の判断、「たぶん問題ない」といった見立て。
- 軸どうしは並行に走らせてよい。Originality 軸は Web 検索を使えるサブエージェントにする。
- **2 回目（`--round 2`）のレンズ**: 1 回目の指摘を直した差分（`git diff HEAD~1`）を中心に、修正による副作用・退行、1 回目で見ていない観点（Standards なら決定性とセーブ、Balance なら長時間遊んだときの経済、Feel ならアクセシビリティ）を重点にする。1 回目の記録（`review-1.md`）を渡し、同じ指摘の繰り返しではなく、直し方の妥当性も確かめさせる。

サブエージェントが使えない環境では、親が 5 軸を順に、軸を切り替えるたびに観点を読み直して審査する。

### 4.3 裏取りと採否

親は、サブエージェントの指摘をそのまま直さない。指摘ごとに次を行う。

1. 根拠のファイルと行、文書の箇所を自分で開いて確かめる。再現できるものは、テストやシミュレーション、ヘッドレス実行で再現する。
2. 採否を決める: **採用**（直す）、**不採用**（理由: 誤読、仕様で許されている、根拠がない など）、**保留**（ユーザーの判断が要る）、**プレイ確認へ**（体感の判定が要る。`[人]` のタスクの観点に足す）。
3. 採否と理由を記録に残す（§5）。不採用の指摘も消さない。

### 4.4 修正

1. CRITICAL と HIGH の採用した指摘は、その場で直す。MEDIUM も原則直す。LOW は直すか、理由を書いて残す。
2. 直し方に複数の選択肢があるとき、仕様の解釈やトレードオフに判断が要るときは、推奨案（`**Recommended:**`）を添えて質問し、合意を得てから直す。自動モード（`--auto`）では `gamekit-worktree` §6 に従う。
3. 仕様の誤りが原因なら、コードだけでなく `spec.md`・`tuning.md`・`plan.md`・`tasks.md` も直す（steering の原則 6）。
4. 直した後、テスト、ヘッドレス実行、（Balance 軸を直したなら）`balance.py check` を実行し、退行がないことを確かめる。

## 5. 記録の様式

機能の工程では `specs/<FEATURE_NAME>/reviews/review-<round>.md`、工程の外では `docs/reviews/<YYYYMMDD>-<対象>.md` に書く。同じ回のファイルがあれば追記する（上書きしない）。

```markdown
# レビュー <round> 回目: <FEATURE_NAME>

- **日付**: YYYY-MM-DD
- **差分**: `git diff <range>`（X files changed, +Y / -Z）
- **エンジン**: godot / gdscript
- **審査の方法**: サブエージェントによる独立審査（軸ごと） / 親による順次審査
- **軸**: Standards, Spec, Balance, Feel, Originality

## 要約

| 軸 | CRITICAL | HIGH | MEDIUM | LOW | 採用 | 不採用 | 保留 | プレイ確認へ |
|---|---|---|---|---|---|---|---|---|
| Standards | 0 | 1 | 2 | 0 | 3 | 0 | 0 | 0 |

## 指摘

### R<round>-<軸の頭文字><連番>: [HIGH] 毎フレーム Array を生成している

- **軸**: Standards
- **対象**: `game/scripts/enemy_spawner.gd#L42-L50`
- **根拠**: `_process` の中で `get_tree().get_nodes_in_group("enemy")` を毎フレーム呼んでいる
- **直し方**: 生成と破棄のシグナルで一覧を保持する
- **採否**: 採用（修正: `abc1234`）

## 未確認・人の確認が要るもの

- Originality: Web 検索が使えず未確認の項目 / 類似の疑いがあり人の確認が要る項目
- Feel: プレイ確認に回した観点（`tasks.md` の T0xx に追記）

## テストの結果

- テスト: PASS（N 件） / ヘッドレス実行: OK / balance.py check: PASS N / FAIL 0
```

指摘の ID は `R<回>-<軸の頭文字（S・P・B・F・O。Spec は P）><連番>`（例: `R1-B03`）。重大度は次のとおりにする。

| 重大度 | 目安 |
|---|---|
| CRITICAL | 憲章・柱の違反、仕様の未達、セーブの破損、クラッシュ、秘密情報の混入、参考作品のテキスト・アセットの流用 |
| HIGH | 毎フレームの重い処理、決定性の破れ、目標値の FAIL、無限に稼げる抜け道、ソフトロック、入力の取りこぼし |
| MEDIUM | コードの匂い、数値の直書き（目標値に影響しないもの）、フィードバックの不足、読みにくい表示 |
| LOW | 軽微な改善 |

## 6. 完了報告

- 記録のファイルのパス
- 軸ごとの指摘の件数と採否
- 直した指摘と、そのコミット
- 保留にした指摘と、ユーザーに判断してほしい事項（選択肢と推奨案）
- プレイ確認に回した観点と、Originality 軸で人の確認が要る項目
- テスト、ヘッドレス実行、バランスの検証の結果
