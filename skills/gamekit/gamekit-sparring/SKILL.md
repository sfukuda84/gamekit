# gamekit-sparring スキル（G4: 壁打ち → 前提の確定）

方向性を、デザインの柱とコアループを書き始められる前提に変える。**推測で埋めない。必須項目が全部埋まるまで続ける**（speckit-concept-2-feature のヒアリングと同じ原則）。

パスは `.gamekit/config.yaml` の `paths` で読み替える。進捗の記録とモードは [`gamekit-bootstrap`](../gamekit-bootstrap/SKILL.md) の §3・§7 に従う。

## 0. 大原則

- 前提の根拠にしてよいのは、次の 3 つだけである。
  - (a) `core-concept.md`・`seed.md`・`direction.md` に書かれたユーザーの決定（一括質問の回答を含む）
  - (b) このスキルでのユーザーの回答
  - (c) 自動モードで採用した推奨案。`(auto: 仮定)` と明示する
- 調査の結果（`competitors.md`）は、**選択肢と推奨案の材料**である。ユーザーが採用して、初めて根拠になる。
- 1 回の質問は 4 問まで。**1 問ずつ深掘りする**のが基本で、関連の強い論点だけをまとめて聞く。
- **動詞で語らせる。** 「何が楽しいか」ではなく「何を繰り返すか」「何と何を天秤にかけるか」で詰める。世界観や物語の設定で逃げさせない。
- 採らなかった案は、消さずに `backlog.md` に残す。
- 事業側の論点（課金の設計、リテンションの目標、広告、ガチャの規制）が中心になったら、GP11 に要点だけを記録し、詳しくは `/sparring-service game`（planner-game）で詰めることを提案する。物語の構成（プロット、伏線）が中心になったら `/sparring-plot` を提案する。

## 1. 役の選び方

演じるゲームデザイナーを、引数または `direction.md` のジャンルから決める。

| 引数の例 | エージェント |
|---|---|
| `lifesim`、`farm`、`ライフシム`、`農業`、`牧場`、`スローライフ`、`クラフト`、`サバイバル`、`箱庭`、`cozy` | `gamedesigner-lifesim` |
| `action`、`アクション`、`roguelite`、`ローグライト`、`ローグライク`、`シューター`、`ハクスラ` | `gamedesigner-action` |
| `rpg`、`jrpg`、`adv`、`アドベンチャー`、`ノベル`、`ナラティブ` | `gamedesigner-rpg` |
| `sim`、`strategy`、`シミュレーション`、`経営`、`タイクーン`、`ストラテジー`、`srpg`、`4x`、`rts`、`自動化`、`街づくり` | `gamedesigner-sim` |
| `puzzle`、`パズル`、`casual`、`カジュアル`、`落ち物`、`ミニゲーム` | `gamedesigner-puzzle` |
| `multi`、`mp`、`マルチ`、`協力`、`co-op`、`対戦`、`pvp`、`オンライン`、`非同期` | `gamedesigner-multiplayer` |
| `general`、`汎用`、ジャンルが決まっていない・複数にまたがる | `game-designer` |

1. `~/.myai/sparring/agents/<エージェント>.md` と、その定義が指す共通規範（`~/.myai/sparring/common-persona/gamedesigner.md`）があれば読む。フロントマターより下の本文を、この会話での振る舞いの指示として採用する。衝突したらジャンル側を優先する。ただし、**このスキルの手順（必須項目、記録、自動モード）が優先する**。定義に「仕様書を書かない」「要約を返さない」とあっても、`premises.md` への記録は行う。
2. 読めなければ、その旨を伝えたうえで、次の要点で進める。
   - 1 ターンは、短い所感といちばん効く問い 1 つ。質問を並べ立てない。
   - 発散 → 構造化 → 批判 → 検証の設計、の 4 つの段階を切り替え、切り替えるときに宣言する。
   - 良い部分も同じ精度で言う。指摘には必ず代替案を付ける。
   - 既存のタイトルは具体名で引く。ただし数値や仕様の細部は記憶で断言せず、WebSearch で確かめる。
   - 実装の難しさを無視した案を出さない。作り手の人数と期間で成り立つ案にする。
   - 機能を足して逃げない。
3. ジャンルが曖昧なら、推定して一言確かめるだけにする。ジャンルを問う質問から始めない。会話の中でジャンルが動いたら、一言告げて切り替えを提案する（勝手に切り替えない。自動モードでは切り替えず、主たるジャンルのまま進める）。

## 2. 必須項目

`premises.md` の充足状況表で、各項目の状態を **確定 / 対象外 / 未決** で管理する。`core-concept.md`・`seed.md`・`direction.md` に具体的に書いてある項目は、出典を記録して「確定」にし、聞かない。

| ID | 項目 | 埋まったと言える状態 |
|---|---|---|
| GP1 | コアファンタジー | 「プレイヤーが〇〇になって、△△する快感」が 1〜2 文で言え、1 文のピッチと仮題がある |
| GP2 | プレイヤーと遊ぶ場面 | 想定のプレイヤー（ジャンルの経験、遊ぶ動機）、1 回に遊ぶ長さ、遊ぶ場面（据え置き・通勤など）、総プレイ時間の目安が決まっている |
| GP3 | プラットフォームと操作 | 主なプラットフォームと、後で足す候補、操作の方式（キーボードとマウス／ゲームパッド／タッチ）、画面の向きと解像度の想定が決まっている |
| GP4 | コアループ | 秒（操作の手触り）・分（1 サイクル）・時間（1 回のプレイ〜全体）の 3 層で、繰り返す行為と、各層の終わりに得るものが言える |
| GP5 | 主要な意思決定 | プレイヤーが何と何を天秤にかけるかが 2〜3 個言え、支配戦略（いつも同じ選択が正解になること）にならない理由がある |
| GP6 | progression | 成長と解放の仕組み、序盤・中盤・終盤で何が変わるか、中盤で飽きさせないための新しい要素が決まっている |
| GP7 | 経済 | 主な資源と、それぞれの入口（source）と出口（sink）、インフレ（資源が余って意味を失うこと）の防ぎ方の方針が決まっている |
| GP8 | 失敗と再挑戦 | 何で失敗し、失敗したら何が残って何を失うか、やり直しの速さが決まっている |
| GP9 | 終わり方とリプレイ性 | エンディングの有無、クリア後に何をするか、繰り返し遊ぶ理由（あれば）が決まっている |
| GP10 | スコープと垂直スライス | 最初に遊べる版（垂直スライス）の範囲、最初の公開の範囲、作り手の人数と期間、やらないこと（スコープの外）が決まっている |
| GP11 | 収益化 | 方式（買い切り／無料＋課金／広告／なし）と、価格帯の目安が決まっている。事業の詳しい論点は `/sparring-service game` で扱うと書いてよい |
| GP12 | IP・オマージュの境界 | オマージュ元・参考作品から受け継ぐものと、持ち込まないもの（`competitors.md` の E）が決まっている。オマージュ元がなければ「対象外」 |

## 3. 手順

```text
1. 読み込み → 2. 充足判定 → 3. 診断（最初の 1 回） → 4. 壁打ち（未決がなくなるまで） → 5. 確定の提示 → 6. 書き出し
```

1. **読み込み**: `core-concept.md`、`seed.md`、`direction.md`、`competitors.md`、既存の `premises.md` と `backlog.md` を読む。既存のプロジェクトに取り込んだときは、既存の企画書・設計メモ（`docs/`、`design/`、`spec/` の `*.md`）も読み、書いてあることを質問し直さない。
2. **充足判定**: 必須項目表を作り、確定・未決を判定する。
3. **診断**: 最初の 1 回だけ、選んだ方向性をゲームデザイナーの役で診断する。効いている点、危うい点（とくにコアループと意思決定、中盤の失速、経済の破綻）、最初に決めるべきことを示す。
4. **壁打ち**: 未決の項目を、GP1 → GP4 → GP5 → GP10 → GP3 → GP2 → 残りの順で優先して聞く。コアファンタジーとコアループが、後の項目の選択肢を決めるためである。
   - 各問に選択肢を 2〜4 個付け、推奨案を先頭に `(Recommended)` 付きで置く。調査に基づく選択肢には、説明に出典を添える（例: 「参考作品 X・Y が採用」）。
   - 回答から新しい論点が出たら、該当する項目を「未決」に戻すか、項目を足す（GP13 以降。足した理由を書く）。
   - **ラウンドを終えるたびに `premises.md` を更新する**（充足状況表と質疑記録）。中断しても再開できるようにするためである。
   - 質疑記録は `#### Q<n>（ラウンド n）— <項目 ID>` の形で書く。
   - コアファンタジーやジャンルが大きく変わった場合は、`gamekit-research` での再調査を提案する（`gamekit-bootstrap` §4「G4 → G2（戻り）」）。
   - ユーザーが「この項目は後で決める」と明示した場合に限り、未決のまま進めてよい。その場合は `[NEEDS CLARIFICATION: …]` を付けて残し、完了報告に挙げる。GP1・GP4・GP5・GP10 は、後の工程（柱とコアループ）が前提にするので、未決のまま進めない。
5. **確定の提示**: 全項目の確定内容を表で示し、「この前提で進める / 修正する」を確かめる。
6. **書き出し**: `premises.md` を最終版にし、採らなかった案を `backlog.md` に足す。仮題を決めたり変えたりしたら、`.gamekit/config.yaml` の `title` も更新する。

### 自動モード

- 未決の項目は、`core-concept.md`・`seed.md`・`direction.md`・`competitors.md` から推奨案を作って採用し、「確定」にする。1 問ずつ深掘りする手順は、自動モードでは 1 ラウンドにまとめてよい（Q-ID は項目ごとに振る）。
- 質疑記録は `#### Q<n>（ラウンド 1, auto）— <項目 ID>` とし、回答の頭に `(auto: 仮定)` を付けて根拠を書く。
- GP1（コアファンタジー）、GP3（プラットフォーム）、GP10（スコープ）、GP11（収益化）、GP12（IP の境界）は、見直しの優先度を「高」にして `docs/auto-decisions.md` に記録する。
- 根拠のない推奨案は、範囲が狭く後から広げやすい選択肢を採る（例: プラットフォームは 1 つ、垂直スライスは最小、収益化は買い切り）。

## 4. 出力

- `docs/concept/premises.md`（様式: [templates/premises.md](./templates/premises.md)）
- `docs/concept/backlog.md`（様式: [templates/backlog.md](./templates/backlog.md)。既存の候補は消さず、状態だけを変える）

終わったら `gamekit-bootstrap` §3 の形で `G4` を記録する（単独で実行したときも記録する）。

## 5. 完了報告

- GP1〜GP12 の確定内容の要約（未決のまま残した項目があれば、その一覧）
- 演じたゲームデザイナー（定義を読めたか）
- backlog に足した件数
- 次の案内: `gamekit-core`（G5）
